# Upgrading to PortForge v1.5.0

> **Do not execute against production.** This guide describes the authorized
> upgrade path. Apply only after publication authorization is granted.

This is the supported upgrade path from v1.4.0 to v1.5.0. It follows the same
deliberate, explicit sequence as previous upgrades — no self-updater, no
automatic migration on Central startup.

## Before you start

**Back up the database first.** Downgrading the v1.5.0 migration drops
deployment history (see [Rollback](#rollback)). A backup is the only reliable
restore path:

```bash
docker run --rm \
  -v portforge_portforge-postgres-data:/data \
  -v $(pwd):/backup \
  alpine tar czf /backup/portforge-db-backup-$(date +%Y%m%d%H%M).tar.gz /data
```

Or use `pg_dump` against your Postgres instance. Store the backup outside the
Docker volume before proceeding.

## Migration path

Single Alembic migration step:

```
c3d4e5f6a1b2  →  d5e6f7a8b9c0
```

New tables introduced by `d5e6f7a8b9c0`:

- `host_deployments` — deployment records, claim leases, state machine
- `deployment_revisions` — per-deployment revision history

No columns are added to existing tables by this migration. Existing host,
allocation, and upgrade records are unaffected.

## Upgrade order: Central first

Always upgrade Central (API + migrations) before upgrading agents. The v1.4.0
agent is compatible with a v1.5.0 Central for all existing functionality;
v1.5.0 deployment features require a v1.5.0 agent but are simply absent until
the agent is upgraded.

### 1. Pull and rebuild Central

```bash
git checkout release/v1.5.0-rc    # or the published tag once authorized
docker compose build portforge-api portforge-dashboard
docker compose up -d
```

### 2. Run the migration

Central does **not** auto-migrate on startup. Run Alembic explicitly:

```bash
# From outside the container:
docker exec portforge-api alembic upgrade head

# Or from inside:
docker compose exec portforge-api alembic upgrade head
```

Verify the head is `d5e6f7a8b9c0`:

```bash
docker exec portforge-api alembic current
```

### 3. Upgrade agents

On each managed host (Windows, Linux, or macOS):

```bash
# Download the new wheel from your distribution point, then:
pip install portforge_agent-1.5.0-py3-none-any.whl --upgrade
portforge agent service install   # idempotent — never rewrites host identity
portforge agent service start
portforge doctor
```

`agent service install` does not touch `~/.portforge/host_id` or
`credentials.json` / `central.json`. Host UUID and enrollment credentials are
preserved across upgrade.

`portforge doctor` should report the agent at 1.5.0 and Central connectivity
healthy. A version mismatch note is advisory only and does not fail the doctor
run.

## Agent compatibility

| Agent version | Central 1.5.0 | Notes |
|---------------|---------------|-------|
| v1.4.0 | Compatible | Existing functionality only; no deployment orchestration |
| v1.5.0 | Compatible | Full deployment orchestration available |

Mixed fleets (some v1.4.0, some v1.5.0 agents) are supported. Upgrade agents
at your own pace after Central is running v1.5.0.

## Rollout recommendation: Central first

1. Upgrade Central + run migration.
2. Verify `portforge doctor` against Central from a client machine.
3. Upgrade dashboard (done as part of Central compose rebuild above).
4. Roll agents one host at a time, verifying `portforge doctor` on each.

## Rollback

**Application rollback and database rollback are separate operations.**

- **Rolling back Central and agents** to v1.4.0 binaries is safe as long as you
  do **not** also roll back the database underneath the newer schema. A v1.4.0
  Central binary running against the `d5e6f7a8b9c0` schema is not tested and
  not recommended.

- **Rolling back the database** (`alembic downgrade c3d4e5f6a1b2`) drops
  `host_deployments` and `deployment_revisions`, permanently losing all
  deployment history recorded since the upgrade. This is irreversible without
  a backup.

- **Recommended rollback path:** restore the database backup taken before
  upgrade, then revert application code to v1.4.0. `alembic downgrade` against
  live data is not recommended for production.

Agent-side state (host identity, enrollment credential, local allocations) is
plain JSON on disk and is unaffected by either direction of a Central rollback.

## What this upgrade does not do

- No automatic Central schema migration on startup.
- No forced simultaneous fleet upgrade.
- No self-updating `portforge upgrade` command.
- No public package repository (PyPI/Homebrew/winget) publishing at this time.
