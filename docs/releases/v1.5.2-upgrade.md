# Upgrading to PortForge v1.5.2

> RC guide — production must not be upgraded until publication is authorized.

v1.5.2 is a reliability release for agent upgrades. It does **not** change
Protocol 1, agent contract 1, machine schema 1, or the database head
(`d5e6f7a8b9c0` — no migration).

## What this fixes for future upgrades

After an agent reports `RESTARTING` and the service manager brings up the new
process, Central reconciles a matching target-version heartbeat to
`VERIFYING_HEALTH` then `SUCCEEDED`. Operators get typed status, bounded retry,
stuck recovery, and canary fleet rollouts.

## Order of operations

1. **Central first** — deploy API `1.5.2` (image or process). Confirm
   `GET /api/health` reports `version: 1.5.2` and `protocol_version: 1`.
2. **Dashboard** — deploy Dashboard `1.5.2`. Confirm `/fleet` and host upgrade
   views load against the new Central.
3. **Agents via controlled rollout** — do **not** restart every host at once.
   Prefer:
   - Create a fleet rollout with `canary_size ≥ 1`, `concurrency` small,
     `stop_on_failure=true`
   - Verify canary `SUCCEEDED` and runtime healthy
   - `advance` remaining hosts
   - On failure: inspect typed status / audit; use operator **retry** (new
     attempt) rather than mutating history

CLI examples (admin bootstrap token via env):

```bash
portforge upgrade status --host-id <uuid> --url http://<central>:58000 --json
portforge upgrade rollout <request_id> --url http://<central>:58000 --json
portforge upgrade retry <upgrade_id> --yes --url http://<central>:58000
portforge upgrade cancel <upgrade_id> --yes --url http://<central>:58000
```

## Mixed fleets

`1.5.1` agents remain Protocol-compatible with `1.5.2` Central. Heartbeat and
enrollment continue. Use canary rollout to move hosts to `1.5.2` agents.

## Historical upgrade rows

- Terminal **`FAILED`** / **`ROLLED_BACK`** / **`SUCCEEDED`** rows are
  **immutable**. Do not SQL-update them to `SUCCEEDED` or `APPROVED`.
- If a host is healthy on the desired version but history shows `FAILED`,
  status may report `RUNTIME_OK_HISTORY_FAILED`. That is truthful: create a
  new attempt only if you need a clean SUCCEEDED history, or leave history as
  audit.
- Non-terminal **`RESTARTING`** / **`VERIFYING_HEALTH`** rows that are still
  the active attempt and meet reconciliation guards (claimed, matching target
  version, host ACTIVE) may advance on heartbeat under Phase 20 rules. Stale
  rows that never get a matching heartbeat become stuck-timeout `FAILED` via
  recover-stuck — they are **not** silently marked SUCCEEDED.

## Mac notes

v1.5.2 preserves the v1.5.1 LaunchAgent KeepAlive form:

```text
KeepAlive = { SuccessfulExit = false, NetworkState = true }
```

Ordinary Mac sleep may show `STALE`/`OFFLINE` without implying upgrade failure.
Do not treat brief Mac sleep as an upgrade FAILED without stronger evidence.

## Rollback

If Central `1.5.2` must be withdrawn before agents move: restore prior Central
image (`1.5.0`). Agents on `1.5.1` remain compatible. Agents already on `1.5.2`
remain Protocol 1 compatible with older Central for heartbeat/sync; avoid
starting new Central-driven upgrades until Central is restored or re-advanced.
