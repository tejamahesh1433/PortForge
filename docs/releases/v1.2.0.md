# PortForge v1.2.0

PortForge v1.2.0 expands the local-first port coordination workflow while retaining protocol 1 and agent contract 1 compatibility. These notes describe the release candidate; they do not indicate that production has been upgraded.

## Highlights

- Range-aware allocation chooses available bindings from requested ranges and validates preferred ports.
- Allocation lifecycle commands support durable request identities, status, point-in-time verification, retry recovery, and explicit release.
- `portforge.yml` consolidates project validation, planning, status, allocation, and local workflow preparation.
- Safe configuration mutation supports explicit plan/apply/rollback for supported dotenv, Docker Compose host ports, and Kubernetes `hostPort`/`nodePort` targets, with containment checks, fingerprints, atomic writes, and post-write validation.
- A provider-neutral, machine-readable coding-agent interface exposes bounded workflows and structured JSON output without arbitrary command execution.
- The operator dashboard covers fleet health, observed ports, projects, reservations, allocations, verification evidence, conflicts, activity, and contextual allocation actions.
- Concurrency and recovery behavior includes idempotent allocation requests, contention handling, reconnect recovery, and durable allocation state.
- GHCR publishing is hardened to stable, published GitHub Releases with least-privilege permissions and immutable third-party action pins.

## Compatibility

- Protocol version: **1**
- Agent contract version: **1**
- Database migration: **none**
- Existing host identity semantics are preserved.
- Legacy `.portforge.yml` behavior remains supported; `portforge.yml` is the preferred consolidated manifest name.

## Upgrade notes

Upgrade Central and agents using the normal deployment process only after release authorization. Existing protocol 1 agents and contract 1 clients remain compatible during a staged upgrade. Existing configuration and database state require no migration for v1.2.0.

Review local project configuration plans before applying them. Configuration mutation is performed by the local CLI on the project host; it is not a browser-driven remote mutation feature.

## Known limitations

- `verified_free` is point-in-time probe evidence only, not a future availability guarantee.
- `requested_range` is transient request input and is not a durable allocation field.
- Rolling back a configuration mutation does not release its allocation.
- Releasing an allocation does not rewrite or roll back local configuration.
- Local configuration mutation is a CLI/local workflow, not browser-based remote mutation.
- Verification of an offline remote host is unavailable until that host reconnects.
- The dashboard intentionally has no browser authentication and is intended only for trusted localhost, LAN, or private-VPN environments.
- PortForge does not provide arbitrary remote command execution.
- Central cannot inspect local manifest contents or local configuration-mutation history that was never sent to it.
- Allocation state and observed listener state are distinct; an active allocation does not prove an application is listening.
