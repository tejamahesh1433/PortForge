# PortForge v1.4.0

PortForge v1.4.0 delivers host lifecycle, fleet intelligence, controlled agent
upgrades, atomic multi-port allocation, project configuration integration, and
a provider-neutral coding-agent interface while retaining protocol 1, agent
contract 1, and machine schema 1. These notes describe the release candidate;
they do not indicate that production has been upgraded.

## Host Lifecycle

- Persistent **Decommission** / **Reactivate** lifecycle on Central and the dashboard.
- Decommissioned hosts reject agent credentials and block new allocations.
- **Remove Record** remains a distinct administrative purge of Central-side state.
- **Remove Record ≠ Decommission.** Decommission does **not** remotely stop,
  uninstall, or wake the machine.

## Fleet Intelligence

- Fleet inventory with health, version, and update-availability views.
- Host detail surfaces agent version and update state without inventing remote shell.

## Agent Upgrades

- Admin-approved, structured upgrade requests with HTTPS artifact URLs.
- Artifacts are **checksum-verified (SHA-256)** before install; mismatch fails closed.
- State machine reports progress to Central; identity files are never rewritten by upgrade.
- Admin **rollback** delivers `allow_downgrade` and a proper wheel filename so the
  previous artifact can install safely.
- Agent upgrade is **not** arbitrary remote shell or generic remote command execution.

## Multi-Port Allocation

- Atomic multi-port allocation bundles with idempotent `request_id`.
- Batch allocation alias and decommissioned-host guards.
- Config apply/rollback preserves allocation until an explicit release.

## Project Integration

- Manifest-driven project inspect / plan / allocate / provision workflow.
- Safe dotenv and Compose mutation; Kubernetes automatic mutation is limited to
  **hostPort** and Service **nodePort** only.
- PortForge does **not** automatically rewrite `containerPort`, Service `port`,
  or `targetPort`.

## Coding-Agent Integration

- Provider-neutral CLI/JSON contract (`capabilities`, `project inspect`,
  `project provision`, workflow prepare/apply).
- Machine schema version **1**.
- **MCP is not included** in this release.

## Security / Safety

- No browser authentication; admin bootstrap secret stays server-side (BFF).
- Upgrade payloads never evaluate as shell commands (`shell=False` subprocesses).
- Local multi-instance overrides (`PORTFORGE_DATA_DIR`, service names) are
  environment-only — never accepted from Central payloads.
- Intended for trusted local / private LAN / VPN deployments — not public Internet.

## Compatibility

- Protocol version: **1**
- Agent contract version: **1**
- Machine schema version: **1**
- Existing host UUID / credential semantics preserved.

## Upgrade notes

Upgrade Central (with Alembic migrations), dashboard, and agents only after
release authorization.

Database upgrade path from a v1.3.0 schema that already includes protocol
columns:

`038acf539985` → `a1b2c3d4e5f6` (host lifecycle) → `c3d4e5f6a1b2` (fleet + host_upgrades)

Downgrade of the latest revision drops fleet columns and `host_upgrades`;
lifecycle columns roll back with `a1b2c3d4e5f6` downgrade. Prefer restore-from-
backup over downgrade in production.

## Known limitations

- Decommission does not remotely stop or uninstall agents.
- No generic remote shell / remote command API.
- Kubernetes mutation remains hostPort / nodePort only.
- MCP deferred.
- Dashboard remains without browser authentication / RBAC.
- No public-Internet deployment mode.
