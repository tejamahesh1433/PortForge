# Upgrading to PortForge v1.5.3

> RC guide — production must not be upgraded until publication is authorized.

v1.5.3 does **not** change Protocol 1, agent contract 1, machine schema 1, MCP
schema 1, or the database head (`d5e6f7a8b9c0` — no migration). It closes the
remaining self-upgrade bootstrap gaps: Linux `rc=-15` false failure, Windows
`WinError 32`, and — new in this release — the macOS path starting from an
**exact published 1.5.2** install (Phase 23C legacy bridge).

## Two upgrade transitions this release supports

### 1. Published 1.5.2 → 1.5.3 (legacy bootstrap)

Published 1.5.2 predates the Phase 23 detached helper, so this hop uses the
Phase 23C bridge instead of the normal helper path:

1. The running 1.5.2 agent installs the 1.5.3 wheel into its own venv
   in-process (unchanged behavior — SHA-256 verified first).
2. It lazily imports the **new** `platform_restart` module from the
   just-installed package.
3. On Linux/Windows this is the same restart call 1.5.2 already made
   (`systemctl --user restart --no-block` / Scheduled Task End+Run) — no
   change needed there, since those platforms didn't have the macOS
   self-bootout problem.
4. On macOS, the new code path schedules an out-of-band kickstarter instead of
   tearing down its own LaunchAgent job in-process, so `KeepAlive={
   SuccessfulExit:false, NetworkState:true}` doesn't leave the job stopped.
5. New 1.5.3 agent heartbeats → Central reconciles `RESTARTING →
   VERIFYING_HEALTH → SUCCEEDED`.

No operator intervention, no manual `launchctl`/`systemctl`/`schtasks`, no
manual `pip install`, on any of the three platforms.

locked RC2 wheel
`2433713d8186ccfbc86d6239984547a1adf333848558b796b2630cfa1956e980` —
Linux / Windows / macOS all **FIRST ATTEMPT PASS**, Central `SUCCEEDED`,
OOB **NO**. Details in
[docs/qualification/v1.5.3-rc2.md](../qualification/v1.5.3-rc2.md).
RC Qualification #1 remains **FAILED** on macOS (pre-Phase-23C); do not
rewrite it.

### 2. Helper-capable N → N+1 (unchanged, normal path)

Any agent that already has the Phase 23 handoff/helper modules (development
1.5.3 onward) upgrades the normal way regardless of platform: typed handoff →
detached helper waits for old PID exit → helper installs + restarts → new
agent heartbeats → reconciliation. Phase 23C did not modify this path — it is
purely additive for the legacy 1.5.2 case.

## Order of operations

1. **Central first** — deploy API `1.5.3`. Confirm `GET /api/health` reports
   `version: 1.5.3` and `protocol_version: 1`.
2. **Dashboard** — deploy Dashboard `1.5.3`. Confirm `/fleet` and host upgrade
   views load against the new Central.
3. **One canary agent** — pick a single host currently on published 1.5.2 (or
   any earlier helper-capable 1.5.x) and roll it to 1.5.3 first. Verify
   `SUCCEEDED` and runtime healthy before touching any other host.
4. **Remaining fleet** — advance via a fleet rollout (`canary_size ≥ 1`,
   bounded `concurrency`, `stop_on_failure=true`), the same controls
   introduced in v1.5.2.

```bash
portforge upgrade status --host-id <uuid> --url http://<central>:58000 --json
portforge upgrade rollout <request_id> --url http://<central>:58000 --json
portforge upgrade retry <upgrade_id> --yes --url http://<central>:58000
portforge upgrade cancel <upgrade_id> --yes --url http://<central>:58000
```

## No manual historical DB edits

- Terminal **`FAILED`** / **`ROLLED_BACK`** / **`SUCCEEDED`** rows are
  **immutable**. Never SQL-update them.
- If a host is healthy on 1.5.3 but history shows `FAILED` from a prior
  attempt, use operator **retry** to create a new attempt row rather than
  editing history.

## Mac notes

v1.5.3 preserves the v1.5.1 LaunchAgent KeepAlive form:

```text
KeepAlive = { SuccessfulExit = false, NetworkState = true }
```

The macOS legacy bridge validates the LaunchAgent label and plist path before
every restart (`com.portforge.agent[.suffix]`, confined to
`~/Library/LaunchAgents/`) and never derives either from a Central payload.
Ordinary Mac sleep may still show `STALE`/`OFFLINE` without implying upgrade
failure — do not treat brief Mac sleep as a FAILED upgrade without stronger
evidence.

## Rollback

If Central `1.5.3` must be withdrawn before agents move: restore the prior
Central image (`1.5.2`). Agents already on `1.5.3` remain Protocol 1
compatible with older Central for heartbeat/sync; avoid starting new
Central-driven upgrades until Central is restored or re-advanced.
