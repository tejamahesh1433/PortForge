# PortForge v1.2.0 release notes (DRAFT)

This document is a release-candidate preparation draft. PortForge v1.2.0 is not released by this document. No tag or GitHub Release is created in Phase 7.

## Changes since v1.1.3

- Range-aware allocation requests with preferred-port validation.
- Project manifests and project-root discovery for validation, planning, status, and allocation workflows.
- Safe, explicit configuration plans and applies for supported dotenv, Docker Compose host ports, and Kubernetes hostPort/nodePort targets. Plans use fingerprints, path containment, atomic writes, post-write validation, and rollback.
- Provider-neutral machine-readable coding-agent workflows with bounded verification, stable request/allocation/plan identities, retry recovery, and secret-safe output.
- Operator dashboard views for fleet health, ports, projects, allocations, verification evidence, conflicts, activity, and contextual release/create/verify actions.

## Upgrade notes

Existing protocol 1 agents and contract 1 clients remain compatible. Existing manifests and allocations require no database migration. requested_range is an allocation request constraint and is not treated as a durable allocation field after creation.

## Security and deployment boundary

The dashboard remains intended for localhost, trusted LAN, or private VPN deployment without browser authentication. PortForge does not provide arbitrary remote command execution, SSH fallback, remote filesystem mutation, process/container control, or firewall/router automation.

## Known limitations

- verified_free is point-in-time probe evidence, not a future availability guarantee.
- Central cannot inspect local manifest contents or local configuration mutation history that was never sent to it.
- Configuration mutation and rollback remain local CLI operations on the project host. Releasing an allocation does not rewrite configuration.
- Offline hosts, including a sleeping laptop, cannot be remotely verified until they reconnect.
- Dashboard allocation and observation state are distinct; an active allocation is not proof that an application is listening.
- v1.2 remains a trusted-network control surface, not a public SaaS control plane.
