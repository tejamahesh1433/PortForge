# PortForge v1.5.0

> **RELEASE CANDIDATE — not published.** These notes accompany the
> `release/v1.5.0-rc` qualification branch. Production has not been upgraded.
> Do not publish, tag, or push until authorization is granted.

PortForge v1.5.0 delivers a native MCP server, workspace discovery, a full
environment/target/ingress model, Compose deployment orchestration with
revision tracking and rollback, and pre-apply port protection with
claim/recovery. Protocol 1, agent contract 1, and machine schema 1 are all
unchanged.

## Native MCP server

`portforge mcp serve` exposes PortForge as an MCP stdio server compatible with
coding agents (Codex, Claude Code, and any client supporting MCP protocol
`2024-11-05`). Registration is:

```
codex mcp add portforge -- portforge mcp serve
# or
claude mcp add -s local portforge -- portforge mcp serve
```

**MCP tools included:**

| Tool | Description |
|------|-------------|
| `portforge_capabilities` | Describe server capabilities and installed feature set |
| `portforge_workspace_discover` | Discover services and internal ports from workspace manifests |
| `portforge_project_plan` | Read-only allocation plan for a project against a target |
| `portforge_deployment_plan` | Read-only deployment plan showing what a Compose apply would do |
| `portforge_deployment_apply` | Submit a Compose deployment for agent execution |
| `portforge_deployment_status` | Poll deployment state, revision, and error detail |
| `portforge_deployment_rollback` | Request rollback to a prior revision |

Claim tokens are internal to the agent/Central interaction and are never
surfaced via MCP.

## Workspace discovery

`portforge workspace discover [path]` (and `portforge_workspace_discover` via
MCP) reads project manifests to enumerate services and their internal
(container/process) ports without connecting to Central. This gives coding
agents a read-only view of what a project declares before planning any
allocation or deployment.

## Environment, target, and ingress model

Project manifests now declare environments (e.g. `development`, `production`)
and named targets (e.g. a specific host) within each environment. Each target
carries an ingress configuration describing how services are reached from
outside the host. This model is the basis for environment-scoped deployment
plans and multi-environment fleet management.

## Compose deployment orchestration

The full deployment lifecycle for Docker Compose stacks:

1. **Plan** (`portforge deployment plan` / `portforge_deployment_plan`) — read-only; no Central record created.
2. **Create / approve** — admin creates a deployment record with `APPROVED` state.
3. **Claim** — agent claims a lease token (`secrets.token_urlsafe(32)`, 300 s). Non-expired claims return the same token on renewal. Stale or mismatched tokens return `409 DEPLOYMENT_CLAIM_MISMATCH`.
4. **Pre-apply port recheck** — declared host ports are verified immediately before `compose up`:
   - `FREE` — no listener, proceed.
   - `EXPECTED_EXISTING_DEPLOYMENT` — Docker publish owned by this deployment's Compose project, proceed.
   - `UNEXPECTED_OCCUPANT` — native listener or wrong project → `DEPLOYMENT_PORT_CONFLICT` (no apply).
   - `UNKNOWN` — discovery failed → fail closed (`DEPLOYMENT_PORT_STATE_UNKNOWN`).
5. **Compose validate + apply** — `compose config` validation, then `compose up`.
6. **Verify + revision** — Central records a revision with SHA-256 of the applied bundle.
7. **Rollback** — admin requests rollback to a prior revision; agent re-applies and records `rollback_revision_id`.

Package transfer uses HTTPS with dual SHA-256 verification (agent-side and
Central-side); checksum mismatch fails closed with
`DEPLOYMENT_CHECKSUM_MISMATCH`. Archive entries with absolute POSIX/Windows
paths are rejected.

## Revision tracking and rollback

Every successful deployment creates a numbered revision record on Central.
Rollback targets a specific `revision_id`; Central records `rollback_revision_id`
on the rollback deployment record so the full chain is auditable.

## Pre-apply port protection

See the recheck algorithm above. The pre-apply check narrows the race between
the final port verification and Docker bind. This is not an OS-level atomic
reservation — see **Residual limitation** below.

## Claim/recovery

Non-terminal deployment jobs with an expired lease (or in `APPROVED` state with
no claim) are re-delivered on the next agent heartbeat `pending_deployment`
response, ensuring interrupted deployments are not silently abandoned.

## Explicit limitations

- **No automatic DNS/TLS/reverse-proxy mutation.** PortForge allocates and
  tracks ports; it does not rewrite DNS records, provision TLS certificates, or
  configure Nginx/Caddy/Traefik/HAProxy on your behalf.
- **No Kubernetes deployment orchestration.** Kubernetes `hostPort`/`nodePort`
  mutation from prior releases is unchanged; Compose deployment orchestration
  does not extend to Kubernetes workloads.
- **No arbitrary remote commands.** Deployment is limited to approved Compose
  stacks delivered via HTTPS with checksum verification. There is no generic
  remote-shell or `docker exec` API.
- **Residual final port-check → bind TOCTOU.** The pre-apply recheck narrows
  but does not eliminate the race window between the last port check and the
  moment Docker acquires the bind. No OS-level socket hold is maintained across
  the apply boundary.
- macOS physical qualification skipped (no SSH / launchd changes avoided in
  production context). Windows and Linux PASS.
- Dashboard remains without browser authentication / RBAC.
- Not intended for public Internet deployment.
