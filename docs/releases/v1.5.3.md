# PortForge v1.5.3

> **RELEASE CANDIDATE — QUALIFIED / FROZEN, not published.** These notes
> accompany `release/v1.5.3-rc2` (RC Qualification #2, built from the Phase 23C
> freeze). Physical Linux/Windows/macOS first-attempt PASS is recorded.
> Production has not been upgraded. Do not publish, tag, push GHCR, or deploy
> until authorization is granted.

PortForge v1.5.3 closes the remaining self-upgrade bootstrap gaps on all three
platforms so an agent can upgrade itself starting from an **exact published
1.5.2** install with no operator intervention, on the first attempt:

- **Linux `rc=-15` false failure** — fixed by the Phase 23 detached helper: the
  running agent process never calls `systemctl restart` on itself. It writes a
  typed handoff, spawns a detached helper that waits for the old PID to exit,
  installs the wheel, then runs `systemctl --user restart --no-block <unit>`.
  No SIGTERM/`rc=-15` from a self-restart is ever interpreted as install
  failure.
- **Windows `WinError 32`** — fixed the same way: the old process exits
  *before* the helper's `pip install` runs, so pip never tries to overwrite
  `Scripts\portforge.exe` while it's held open by the running interpreter.
- **macOS exact published 1.5.2 → 1.5.3** — published 1.5.2 predates the
  Phase 23 helper entirely, so the legacy-bridge fix (Phase 23C) is additive:
  1.5.2 installs the target wheel in-process (unchanged), then *lazily
  imports* the **new** `platform_restart.restart_via_launchctl`, which
  schedules an out-of-band kickstarter (`Popen` + `start_new_session`) that
  waits for the calling PID to exit and then
  `launchctl kickstart -k gui/<uid>/<label>` (bootstrapping the known plist
  first if needed). The old code path — an in-process `launchctl bootout` of
  its own job — is gone; that path is what previously left `KeepAlive={
  SuccessfulExit:false, NetworkState:true}` launchd jobs stopped with Central
  stuck at `RESTARTING`.

**Unchanged:** Protocol 1 · Agent contract 1 · Machine schema 1 · MCP schema 1
· DB head `d5e6f7a8b9c0` (no migration) · macOS LaunchAgent KeepAlive
`{SuccessfulExit: false, NetworkState: true}` preserved from v1.5.1.

## FIXED / ADDED

### Phase 23 — detached self-upgrade helper (Linux, Windows)

- Structured upgrade payload validated with no network I/O
  (`command`/`script`/`executable`/`shell` fields rejected outright,
  `artifact_sha256` format-checked, `artifact_url` scheme/host-checked).
- SHA-256 verified before any install; fails closed on mismatch.
- Typed handoff record (`host_id`, `nonce`, `python_executable`,
  `artifact_sha256`, stage) written locally, then a detached helper process is
  spawned that: waits for the old PID to exit → re-verifies SHA-256 → `pip
  install --upgrade --force-reinstall --no-deps <verified wheel>` → restarts
  the service via a hardcoded platform adapter — never a payload-derived
  command.
- Helper is idempotent under duplicate invocation (nonce + nonce-aware lock).

### Phase 23C — legacy macOS bootstrap bridge

- Additive-only: does not change the Phase 23 helper-capable path for any
  agent ≥ development 1.5.3 that already has handoff/helper modules.
- Restart identity is validated before any macOS restart: LaunchAgent label
  must match `com.portforge.agent` or `com.portforge.agent.<suffix>`, and the
  plist path must resolve under `~/Library/LaunchAgents/` — both refuse
  closed on anything else. Neither ever comes from the Central payload; only
  local `PORTFORGE_MACOS_PLIST_LABEL` / `PORTFORGE_MACOS_PLIST_PATH`
  overrides or built-in defaults.
- The kickstarter's argv is a fixed list (`launchctl kickstart -k ...` /
  `launchctl bootstrap ...`), no `shell=True` anywhere in the module.

### Security boundary (both paths)

No generic shell, no generic remote command, no arbitrary executable, args,
service, URL, install path, or LaunchAgent label. All subprocess execution is
narrowly constrained to fixed argv lists with locally-validated identifiers.
