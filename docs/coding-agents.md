# PortForge for Coding Agents

PortForge acts as the definitive Port Authority for environments heavily utilizing AI Coding Agents (such as Antigravity).

If you are an autonomous coding agent building a project in an environment governed by PortForge, **you must never guess or hardcode ports**. You must interface with the PortForge CLI to request safe port allocations.

## Discovering PortForge
Coding agents should first verify PortForge is installed. Typically, environments will mount or place an agent contract (e.g. `docs/agent/portforge-tool-contract.json` or `PORTFORGE_AGENT.md`) detailing the CLI schema.
Run `portforge agent-contract` to output the JSON schema detailing the rules of engagement.

## The Agent Workflow
When spinning up a new service or full-stack project, follow these steps:

1. **Write `portforge.yml`**:
   Initialize a PortForge manifest defining the ports required.
   ```bash
   portforge project init
   ```
   Modify `portforge.yml` to match your service requirements.

2. **Prepare (Reserve)**:
   ```bash
   portforge workflow prepare --json
   ```
   This communicates with Central to compute available ports and creates a temporary advisory lock.

3. **Apply (Allocate)**:
   ```bash
   portforge workflow apply --json
   ```
   This commits the reservation into a permanent allocation and mutates the project's `.env` and `docker-compose.yml` to reflect the newly granted ports.

4. **Consume**:
   Configure your application (e.g. Next.js, Express, PostgreSQL) to read from the environment variables (e.g., `PORT_FRONTEND`, `PORT_DATABASE`) generated by PortForge.

## Handling Interruptions (Idempotency)
If you crash or lose connection mid-workflow, do not panic and do not start over with a new project name.
Retrying `portforge workflow apply` is entirely safe and idempotent. PortForge tracks requests by a `request_id` generated during `prepare`. Retrying an operation will safely re-fetch your existing allocation rather than leaking resources.

## Central Outages
If the Central API is offline, `workflow apply` will fail gracefully.
Do not bypass PortForge. Halt your deployment, report the outage to the user, and retry `workflow apply` when Central is back online.

## Rollback & Release
If your stack fails to bind (e.g. an unmanaged process stole the port), you must clean up:
```bash
# Execute the release command provided in the output of the failed apply/prepare, or manually:
portforge allocation release <request_id>
```

**CRITICAL RULE:** Coding agents must NEVER select manual fallback ports (e.g., "I will just try 3001") when PortForge is configured as the port authority.
