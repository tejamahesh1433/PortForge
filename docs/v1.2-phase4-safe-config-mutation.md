# PortForge v1.2 Phase 4: Safe Project Configuration Mutation

## Existing engine

Phase 4 reuses the Phase 8C mutation engine in config_manager.py. It is one
pipeline for plan, persistence, apply, status, and rollback. The target editors
are dotenv_editor.py, compose_editor.py, and k8s_editor.py; path checks and
atomic writes live in config_files.py.

## Supported targets

- Explicit .env mappings update only declared keys. Comments, unrelated lines,
  ordering, and newline style are preserved where the format permits.
- Docker Compose mappings update only the published host side of an explicitly
  targeted service/container/protocol mapping. Bind addresses and protocol
  suffixes remain unchanged. Container ports are never rewritten.
- Kubernetes mappings update only explicitly targeted hostPort or nodePort
  fields. containerPort, Service port, and targetPort remain unchanged.
  NodePort values use the existing supported local-cluster range validation.

JavaScript, TypeScript, Python source, inferred files, and arbitrary framework
configuration are unsupported unless represented by an explicit existing target
mapping.

## Lifecycle

config plan validates allocation ownership, requires an active allocation,
resolves explicit targets, fingerprints every file, and persists a mutation
record without writing project files. The plan contains the allocation ID,
mutation ID, target paths, operation kind, before hashes, and proposed changes.

config apply resolves the same allocation again, rejects released or mismatched
allocations, checks every fingerprint immediately before writing, then writes
all targets through sibling temporary files and atomic replacement. The rendered
Compose and Kubernetes files are parsed again after writing. Any write or
validation failure restores files already written in that operation.

config status is read-only. config rollback restores the byte-for-byte backups
only when every target still matches the post-apply fingerprint. Rollback never
releases an allocation; allocation release never rewrites config.

## Safety boundaries

Manifest paths are resolved beneath the project root before reads or writes.
Traversal, absolute paths outside the root, and symlinks that resolve outside
the root are rejected. Two plans for the same file are safe because the second
apply fails its stale-file check after the first changes the file.

Secret-looking dotenv keys redact their previous values in plan/apply/status
output. Port values are safe to display. JSON commands emit structured data
without unrelated file contents.

## File behavior

Existing file permissions are preserved during atomic replacement where the
platform exposes them. UTF-8 is used for generated content; dotenv newline
style is retained. Compose and Kubernetes use round-trip YAML editors with
explicit mappings rather than broad document rewrites.

## Non-goals

Phase 4 does not orchestrate processes, probe remote agents, release
allocations, mutate arbitrary project files, change protocol or contract
versions, add a database migration, deploy development code, or alter the
dashboard.
