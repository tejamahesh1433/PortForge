# PortForge v1.2 Phase 5: Automation Contract

## Audit result

Phase 1 through Phase 4 already provide machine-readable CLI paths for project
inspection, validation, allocation lifecycle, verification, and configuration
mutation. Phase 5 standardizes their usage and documentation without replacing
existing JSON payloads or breaking consumers.

The established error shape is:
{"error": {"code": "...", "message": "...", "details": [...]}}.
Success payloads remain command-specific because existing automation consumers
already depend on them. Operation identity is the command path itself
(project.status, project.validate, allocation.create, allocation.get,
allocation.verify, allocation.release, config.plan, config.apply, and
config.rollback).

No new protocol, agent-contract, database, or provider metadata was added.
The agent contract remains the read-only capability discovery surface.

## Contract matrix

| Operation | CLI | JSON | Mutates lifecycle | Retry guidance |
| --- | --- | --- | --- | --- |
| project.status | yes | yes | no | repeat freely |
| project.validate | yes | yes | no | repeat freely |
| allocation.create | yes | yes | yes | reuse request ID |
| allocation.get/list | yes | yes | no | repeat freely |
| allocation.verify | yes | yes | probe record only | repeat within bounded verification |
| allocation.release | yes | yes | yes | safe idempotent replay |
| config.plan | yes | yes | local plan record | repeat creates a new plan |
| config.apply | yes | yes | files + mutation record | repeat same applied plan is a no-op |
| config.rollback | yes | yes | files + mutation record | repeat completed rollback is a no-op |

## Error and exit contracts

JSON errors preserve stable existing codes such as MANIFEST_INVALID,
ALLOCATION_NOT_FOUND/existing allocation lookup codes, ALLOCATION_INACTIVE,
CONFIG_CHANGED_SINCE_PLAN, CONFIG_PATH_OUTSIDE_PROJECT, and
CONFIG_VALIDATION_FAILED. Exit code 0 means success, 1 means an expected
domain/resource/conflict failure, and 2 means invalid input or operational
setup failure.

Central-unavailable and offline-agent paths return bounded structured failures;
local manifest validation remains usable without Central. Remote verification
keeps the Phase 2 bounded wait behavior.

## Security

JSON mode never serializes enrollment credentials, SSH keys, tokens,
authorization headers, or full environment/config contents. Config mutation
output exposes relative target paths, field names, and port changes only.
PortForge has no provider-specific fields and no arbitrary remote execution
interface.

## Deliberate non-goals

No alternate automation API, provider SDK, database migration, protocol change,
dashboard redesign, or direct Central-to-filesystem mutation path was added.
