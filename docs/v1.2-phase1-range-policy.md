# PortForge v1.2 Phase 1: Range Policy

## Objective
Extend the existing PortForge allocation/recommendation architecture with first-class range constraints, allowing callers to specify custom inclusive minimum and maximum port bounds during allocation.

## Contract Changes

1. **Request Payload (`AllocationRequestItem`)**:
   - Added `requested_range` string (format: `MIN-MAX`) to the JSON schema.
   - Preserves backward compatibility (omission defaults to existing service-based range rules).

2. **Response Payload (`AllocationEntryOut`)**:
   - Added `requested_range` string to the response, exposing the range constraint used.
   - Enables JSON automation contract for coding agents to determine effective range policies.

3. **CLI Usage**:
   - `portforge allocate --request NAME:PURPOSE[:PROTOCOL[:PREFERRED_PORT_OR_RANGE[:RANGE]]]`
   - Example 1: `portforge allocate --request api:api:tcp:8000-8999`
   - Example 2: `portforge allocate --request myapp:frontend:tcp:8127:8127-8127`

## Engine Semantics

1. **Deterministic Failure**:
   - If the range is completely exhausted (all ports within the range are claimed), the allocation will fail cleanly with no available port.

2. **Idempotency**:
   - `requested_range` is strictly included in the canonical JSON payload hashed for `request_id` replay protection. Re-requesting the identical bundle (including the range constraint) with the same `request_id` securely returns the identical allocation.

3. **Persistence**:
   - `requested_range` acts as transient selection input to the algorithm. 
   - We consciously opted to avoid a schema migration of the `CentralReservation` model. Instead, when a `GET /allocations/{id}` request reconstructs the output, the `requested_range` field remains unbound unless the original payload is supplied during an immediate idempotent re-request.
   - For `allocate` calls, the response faithfully mirrors the client's transient range constraint.

## Validation bounds
- Both bounds are strictly integers.
- Must satisfy: `1 <= min <= max <= 65535`.

## Future Phases
Phase 2 will build upon this foundation to introduce enhanced code-agent interfaces.
