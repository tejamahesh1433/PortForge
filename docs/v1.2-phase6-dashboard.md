# PortForge v1.2 Phase 6: Dashboard and operator control surface

Phase 6 keeps the dashboard as a trusted-network operator console for Central. It composes existing Central APIs and lifecycle services; it does not duplicate allocation logic.

## Information architecture

The existing routes provide Overview, Hosts (including host detail), Ports, Projects (including project detail), Reservations, Allocations (including allocation detail), Conflicts, Activity, Diagnostics, Recommendations, and Settings. Overview links summary metrics to the underlying pages.

## Data sources and health

Fleet, port observations, projects, reservations, allocations, conflicts, activity, and health are read from the existing typed Central API client. Host health uses the backend-provided health state when present and the existing recency fallback otherwise. HEALTHY, STALE, OFFLINE, and DEGRADED remain distinct. Mixed agent patch versions are displayed as information; the UI does not treat a 1.1.1/1.1.2 fleet as an error.

The Mac can remain offline or stale as a normal laptop condition. Its state is shown with last-seen context and does not cause the dashboard to fail for the rest of the fleet.

## Allocation lifecycle actions

Allocation creation uses the existing POST /api/allocations contract and Phase 1 range validation. The dashboard sends project, host, protocol, service/purpose, preferred port, requested range, and the backend remains authoritative. Allocation detail exposes an explicit verify action through POST /api/allocations/{id}/verify; pending state prevents duplicate clicks and the authoritative allocation is refetched after completion.

Release uses the existing idempotent DELETE /api/allocations/{id} contract. It requires contextual confirmation showing project, host, and binding count. Release changes PortForge ownership state only: it does not stop a process, kill a container, or rewrite project files.

verified_free is shown as evidence that the binding was free at the time of the last probe. It is not a future availability guarantee, and occupied evidence is not automatically labeled a conflict.

## Projects and configuration boundary

Central shows only project and allocation data it actually receives. Local portforge.yml contents remain a CLI capability; the browser does not inspect arbitrary project directories. Phase 4 configuration mutation remains local to the project host through PortForge CLI. The dashboard has no remote file editing, arbitrary command execution, SSH fallback, process control, container control, or network-device mutation.

## Polling, loading, and errors

React Query uses the existing bounded polling and stale-time configuration. Initial loads use skeletons; background refresh retains existing data. Errors distinguish Central connection failures and HTTP responses without exposing stack traces or credentials. Manual retry is available on page-level failures, and verify explicitly invalidates allocation-related data.

## Accessibility and responsive behavior

Actions use labeled buttons, keyboard-reachable confirmation dialogs, visible focus styles, text state labels in addition to color, and responsive grids/tables for laptop and tablet widths. Empty states distinguish no data from filtered results and offline hosts.

## Known limitations

Central cannot display local manifest fields or local config mutation history that was never sent to Central. Config plans and applies remain local. Port observations, reservations, allocations, verification evidence, and conflicts are separate concepts in the UI; an allocation is not a claim that an application is listening.

## Deployment boundary

The dashboard remains intended for localhost, trusted LAN, and private VPN deployments. Browser authentication and public Internet control-plane behavior are intentionally out of scope for this phase.
