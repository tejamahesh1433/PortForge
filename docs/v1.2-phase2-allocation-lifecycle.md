# v1.2 Phase 2: Allocation Lifecycle

## Overview
Phase 2 turns the existing allocation functionality into a complete operational lifecycle suitable for both humans and coding agents.
The new capabilities include listing allocations, checking their status, explicitly verifying them, and releasing them idempotently.

## Endpoints
- `GET /api/allocations` (List allocations) - already existed, but enhanced in CLI usage.
- `GET /api/allocations/{id}` (Status) - existing endpoint.
- `POST /api/allocations/{id}/verify` (Verify) - new endpoint. Queues remote probes and polls for results (up to 10s) before returning fresh evidence.
- `DELETE /api/allocations/{id}` (Release) - already existed, but modified in CLI for idempotency mapping 404 to "already released".

## CLI Commands
- `portforge allocation list`: List all allocations with their current evidence and state.
- `portforge allocation status <id>` (alias for `get`): View detailed status of a single allocation.
- `portforge allocation verify <id>`: Actively probe all ports within the allocation to check listener status.
  - Local host: Bypasses the network, uses the agent's internal `bind_probe` directly for immediate feedback.
  - Remote host: Calls the new `POST /verify` backend endpoint, which coordinates with the target agent via heartbeat and waits for the result.
- `portforge allocation release <id>`: Idempotently releases the allocation.

## Idempotency Considerations
- Releasing an already-released allocation acts as a no-op success instead of erroring out. If `DELETE` returns 404 (ALLOCATION_NOT_FOUND), the CLI explicitly translates this into a successful "RELEASED" semantic for agents recovering from missed network responses.
