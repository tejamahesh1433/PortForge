# v1.1-B Implementation: Authoritative Remote Host Bind Probing

Implements the scope of `docs/v1.1/roadmap.md`'s v1.1-B increment, grounded
in `docs/v1.1/remote-probe-design.md` (the pre-approved design this
increment follows — specifically its "queued probe request delivered on
heartbeat" transport choice and its 5-value `bind_probe` contract). Builds
directly on `v1.1-A`'s canonical version source and protocol-compatibility
machinery (`docs/v1.1/v1.1-a-implementation.md`); no v1.0/v1.1-A contract
was removed or renamed.

## 1. Architecture

Central cannot bind a socket on a remote host — only the agent running on
that host can perform an authoritative local check. This increment adds a
queued-request/delivered-on-heartbeat pipeline using the **existing**
authenticated agent↔Central channel, with no new transport:

```
Central queues a HostProbe row (PENDING)
        |
        v
Agent's next heartbeat response includes it (pending_probes[])
        |
        v
Agent runs the SAME local bind-then-close check `portforge check` already
uses (bindprobe.py::probe_bind) -- no second definition of "free"
        |
        v
Agent POSTs the result to /api/agent/probes/result (authenticated)
        |
        v
Central validates host ownership + records COMPLETED/FAILED
        |
        v
Recommendation/allocation consult the result IF still fresh (TTL)
```

No SSH, WinRM, remote shell execution, or new signing infrastructure was
introduced. The probe payload's only operation is "bind-then-close this
port/protocol/address" — never an arbitrary command.

## 2. Database model and migration

`backend/app/models/host_probe.py::HostProbe` — new table `host_probes`:
`id`, `host_id` (FK → `hosts.id`), `port`, `protocol` (shared `protocol`
enum, reused from the existing schema), `bind_address`, `status`
(`PENDING`/`DELIVERED`/`COMPLETED`/`FAILED`), `result_available`
(nullable bool), `result_reason`, `delivered_at`, `completed_at`,
`expires_at`, plus the standard `TimestampMixin`.

`"expired"` is deliberately **not** a stored status — it's always derived
at read time (`classify_bind_probe()`) by comparing `expires_at` to now.
This avoids a background sweep job and avoids a race between "is it
expired" and "what does the status column say."

Migration `backend/alembic/versions/d6bcb4da5c4b_add_host_probes.py`.
Real bug found and fixed during this increment: Alembic's autogenerate
emitted `sa.Enum('tcp','udp', name='protocol')`, which tried to
`CREATE TYPE protocol` again and failed with `DuplicateObject` — the
`protocol` enum type already exists, created by the initial schema
migration for other tables. Fixed with
`postgresql.ENUM('tcp', 'udp', name='protocol', create_type=False)`.
Verified via upgrade → downgrade → re-upgrade cycles, fresh-database
upgrade, and all 7 `test_migrations.py` tests. No existing table,
reservation, or allocation semantics were touched by this migration.

## 3. Probe lifecycle

`backend/app/services/probe_service.py` owns the whole lifecycle:

- **`queue_probe(db, host_id, port, protocol, bind_address)`** — fire and
  forget. Returns `None` (no probe created, no error) if: the host doesn't
  exist, the host isn't `HEALTHY` (reuses `derive_health_state` — see §7),
  or `max_pending_probes_per_host` (default 20) would be exceeded.
  Deduplicates: an existing active (`PENDING`/`DELIVERED`, unexpired) probe
  for the exact same `(host_id, port, protocol, bind_address)` is reused
  instead of creating a duplicate row. **Only flushes, never commits** —
  see §12's bug write-up for why this matters.
- **`claim_pending_probes(db, host_id)`** — called from the heartbeat
  handler; marks up to `max_probes_delivered_per_heartbeat` (default 5)
  `PENDING` probes `DELIVERED` and commits (this is the heartbeat
  handler's own transaction boundary, not a side effect of something
  else).
- **`submit_result(db, authenticated_host_id, probe_id, available,
  reason)`** — validates `probe.host_id == authenticated_host_id`
  (`ProbeOwnershipError` otherwise, see §5); idempotent (first submission
  wins; a repeat submission to an already-`COMPLETED`/`FAILED` probe
  returns the existing row unchanged); `available=None` means the probe
  *attempt itself* errored (network/socket failure), recorded as `FAILED`,
  distinct from `available=False` (the port really is occupied).
- **`classify_bind_probe(probe, now=None)`** — pure function producing one
  of the 5 `bind_probe` contract values (§6). Checks `expires_at` *before*
  status, so a `COMPLETED`-but-stale probe is correctly classified
  `expired`, never trusted as current.

## 4. Agent protocol additions

`backend/app/schemas/agent.py::HeartbeatResponse` gained
`pending_probes: List[PendingProbeOut] = []` — additive, defaults to an
empty list, so an agent binary predating this field simply never sees it
populate anything it reads.

New endpoint `POST /api/agent/probes/result` (`backend/app/api/agents.py`)
— authenticated via the existing `require_agent` bearer-token dependency,
same as every other agent-facing endpoint. Payload: `host_id`, `probe_id`,
`available` (nullable bool), `reason` (optional string). Rejects a
mismatched `host_id` with 403 before ever touching `probe_service`.

Agent side: `agent/portforge_agent/central_client.py::submit_probe_result()`
(authenticated POST) and `agent/portforge_agent/remote_probe.py`
(`process_pending_probes(client, heartbeat_data)`), the single shared
module used identically by both the one-shot `portforge central sync`
(`central_sync.py`) and the always-on daemon (`runtime/agent.py`). It:
bounds each cycle to `MAX_PROBES_PER_CYCLE = 10` entries, skips (not
crashes on) any malformed entry, reuses `bindprobe.py::probe_bind()` — the
exact bind-then-close logic `portforge check` already uses — and never
raises, so a probe-processing failure can never break the heartbeat loop
or the sync command.

## 5. Host authorization

A probe belongs to exactly one host (`host_id` FK). Only the
authenticated agent for *that* host can receive it (delivery is scoped by
`claim_pending_probes(db, host_id)`, called with the requesting agent's
own authenticated `host_id`) or submit a result for it
(`submit_result`'s `authenticated_host_id == probe.host_id` check, backed
by the existing per-host bearer token from `require_agent` — not a
client-supplied UUID in the JSON body, which would be spoofable). Verified
physically and in `test_api_probes.py`
(`test_host_a_cannot_receive_host_b_pending_probe`,
`test_host_a_cannot_submit_result_for_host_b_probe`).

## 6. Freshness / TTL and the `bind_probe` contract

`remote_probe_ttl_seconds` (default 120s, `backend/app/config.py`) governs
freshness. Five `bind_probe` values (v1.0's `"not_remote_capable"` is
unchanged — no removal, no rename):

| Value | Meaning |
|---|---|
| `not_remote_capable` | v1.0 default — no probe evidence exists or was ever attempted for this candidate (also the fallback whenever there's genuinely nothing better to report). |
| `verified_free` | A `COMPLETED` probe, still within TTL, reported the port free. The only value that can upgrade a recommendation's `verification` to `"locally_verified"`. |
| `verified_occupied` | A `COMPLETED` probe, still within TTL, reported the port occupied — that candidate is rejected/excluded, never allocated. |
| `unavailable` | The probe attempt itself failed (agent-side socket error unrelated to occupancy), or no probe could be queued (e.g. host offline). Evidence is missing, not "free." |
| `expired` | A probe exists but its `expires_at` has passed — never trusted as current, regardless of what it once said. |

Missing evidence is never silently treated as "free" anywhere in this
code path — `_port_is_free()` and `resolve_with_probe_awareness()` only
ever *exclude* on `verified_occupied`; they never *include* on the
absence of a probe.

## 7. Recommendation integration

`recommendation_service.suggest_port()` calls `find_available_port()` for
the initial candidate, then
`probe_service.resolve_with_probe_awareness(db, host_id, protocol,
initial_result, refine)` — a shared, bounded (max 5 attempts) retry loop
also used by allocation (§8), taking a `refine` callback rather than
importing `find_available_port` directly (avoids a circular import
between `recommendation_service.py` and `probe_service.py`, since the
latter is already imported by the former). `verification` is set to
`"locally_verified"` only when `bind_probe == "verified_free"` — the
first code path in this codebase ever able to produce that value for
real. Central never treats its own local socket probing as evidence for
a *remote* host; a host with no probe support (legacy agent, see §9) or
no fresh evidence simply stays at `"central_suggestion"` /
`"not_remote_capable"`, honestly.

`suggest_port()` also gained an explicit `db.commit()` at the end — see
§12's second bug write-up for why.

## 8. Allocation integration

`allocation_service._port_is_free()` additionally checks
`probe_service.get_probe_evidence(...)` and rejects a candidate on
`verified_occupied`, even though nothing in the reservation table itself
knows about that occupancy. `_resolve_candidate()` now returns
`(port, bind_probe)`: for a `preferred_port` request it checks probe
evidence directly (queuing a probe if none exists yet) rather than
blindly trusting the preference; for the search path it uses the same
`resolve_with_probe_awareness` loop as recommendations.

Because one allocation response carries a single `bind_probe` field for
the whole bundle (not one per port), `create_allocation()` tracks
`bundle_bind_probe` — the *strongest* evidence seen across every resolved
candidate in the bundle (`verified_free` beats everything else) — and
surfaces it only on the CREATE path; `GET`/release responses keep the
`"not_remote_capable"` default, since they didn't just resolve anything.

Host-scoped advisory locking (`pg_advisory_xact_lock`), reservation
atomicity, idempotency, and bundle allocation semantics from Phase 8A are
unchanged and unweakened — proven by the existing Phase 8A concurrency
tests still passing plus two new ones (§13). **This does not solve the
probe→allocation→application-bind race** — see §11.

## 9. Legacy-agent compatibility

No explicit "is this agent legacy" branch exists anywhere. `pending_probes`
is delivered unconditionally in every heartbeat response; an older agent
binary that has no code to read that field simply never acts on it —
compatibility falls out of the schema being additive-only, not from a
capability negotiation. Central continues to sync such a host under full
v1.0 rules; it just never queues probes that would go nowhere in
practice (the host still receives them, they just expire unclaimed,
harmlessly, since `queue_probe`'s dedup means Central doesn't keep piling
up new ones for the exact same binding).

## 10. Offline / stale-host behavior

`queue_probe()` refuses to create a probe for any host that
`derive_health_state()` — the same function allocation already uses to
refuse allocation to unhealthy hosts — doesn't report `HEALTHY`. No new
host-liveness logic was invented. An offline/stale host therefore never
accumulates queued probe work it can never answer.

## 11. Security model and the TOCTOU limitation

The probe operation is bind-then-close only — no listener persists, no
process is killed, no container is stopped, no reservation is released,
no firewall/OS config changes, no project files are touched, bounded by
the agent's own HTTP timeout. Host ownership is enforced by the
already-established per-host bearer token, not a client-supplied UUID.
No token, password, or credential value is ever logged by probe
processing (`test_no_secrets_logged`).

**This increment does not, and architecturally cannot, eliminate the
race between a probe result and an actual application bind.** This was
proven physically, not just asserted: in the §14 race test below, a
probe for port 16600 on lenovoserver completed as `verified_free`; an
external process then bound that exact port; an allocation request for
the same port, made immediately afterward while that probe result was
still within its 120-second TTL, **consumed the stale-but-still-fresh
evidence and returned `port: 16600, bind_probe: "verified_free"`** —
despite the port being genuinely occupied by another process at that
literal moment. Probing raises confidence versus a pure central-side
guess; it does not, and is not claimed to, close the fundamental
probe-to-bind race. This is documented here deliberately, not fixed,
per the increment's explicit instruction not to overclaim.

## 12. Real bugs found and fixed during implementation

1. **Alembic ENUM `create_type` collision** — see §2.
2. **`queue_probe()` committing internally broke the allocation advisory
   lock.** `queue_probe` originally called `db.commit()`. Since
   `_resolve_candidate` (inside `create_allocation`, which holds a
   transaction-scoped `pg_advisory_xact_lock` for the whole bundle) calls
   `queue_probe` as a side effect, that commit prematurely ended the
   transaction and released the lock early — caught by
   `test_concurrent_allocations_same_host_same_purpose_never_collide`
   failing (both threads got port 8000). Fixed by making `queue_probe`
   only `db.flush()` (matching `AllocationRepository.add()`'s own
   convention); the caller's own eventual commit/rollback now covers the
   probe row like any other change in that transaction. Because
   `recommendation_service.suggest_port()` owns its own transaction
   boundary and the API handler never commits, `suggest_port()` gained an
   explicit trailing `db.commit()` to still persist a probe queued as a
   side effect there.
3. **Duplicate probe rows for the identical binding.** A test that both
   triggered an auto-queued probe (via `GET /api/recommendations`) and
   then manually queued another probe for the same
   `(host_id, port, protocol, bind_address)` produced two rows with
   possibly-tied `created_at`, making "latest" ordering ambiguous. Fixed
   by having `queue_probe` return an existing active probe for the same
   binding instead of creating a second one — a genuine correctness fix
   that also directly serves the "no unbounded queue growth" requirement.

## 14. Physical multi-host acceptance summary

All physical scenarios were run against the real fleet (NTMKEYA,
lenovoserver) through the same bare-process Central used for v1.1-A
(Docker Desktop DNS issue still present on this dev machine — see §15;
not touched).

- **§18 occupied remote port** — a real listener on lenovoserver port
  19600 (independently verified via `ss -tlnp`) produced `COMPLETED,
  result_available=False, reason="bind failed: [Errno 98] Address already
  in use"` — a genuine kernel-level error from lenovoserver. The port was
  excluded from `GET /api/recommendations`. Listener removed, confirmed
  via `ss`.
- **§19 free remote port** — port 10001 on lenovoserver: fresh probe
  completed, `GET /api/recommendations` returned
  `verification: "locally_verified", bind_probe: "verified_free"` (the
  first time this codebase has produced `"locally_verified"` for real);
  allocated via `POST /api/allocations`, confirmed host UUID matched
  lenovoserver and `validation.bind_probe: "verified_free"`. Released
  during final cleanup.
- **§20 same numeric port, different hosts** — port 15000 allocated
  independently and successfully on both NTMKEYA
  (`dbd157b4-8f71-4fc4-8898-de6abb85ab2f`) and lenovoserver
  (`b9ef55ae-6718-49c2-ab29-2df244fc9394`) — no false cross-host conflict.
  Both released during final cleanup.
- **§21 race (TOCTOU)** — described in full in §11. Port 16600 on
  lenovoserver: probe completed `verified_free`; an external listener
  then bound the port; an allocation request for the same port, made
  while that evidence was still within TTL, returned
  `port: 16600, bind_probe: "verified_free"` despite the port being
  occupied at that moment. Listener killed, allocation released,
  independently verified clear via `ss`.
- **§22 concurrency** — 6 concurrent `POST /api/allocations` requests
  fired in parallel at lenovoserver (same purpose, no preferred port) all
  succeeded with 6 distinct ports (10002–10007), no duplicates — the
  host-scoped advisory lock held under real concurrent HTTP load, not
  just the unit-level thread tests. All released.
- **§16 agent restart mid-probe** — a probe was queued
  (`PENDING`), lenovoserver's `portforge-agent.service` was restarted via
  `systemctl --user restart` before its next heartbeat could deliver it,
  and the restarted agent's next heartbeat safely delivered and completed
  it (`COMPLETED, result_available=True`) with no duplicate row for the
  same binding.
- **§17 Central restart mid-probe** — a probe was queued, the bare-process
  Central was killed and restarted fresh (same Postgres, same bootstrap
  token), and lenovoserver's next heartbeat against the *new* Central
  process correctly delivered and completed the probe — proving the
  Postgres-backed `HostProbe` row, not an in-memory structure, is the
  actual source of truth.

## 15. Known limitations

- **Docker Desktop DNS** — carried over from v1.1-A, still present on
  this dev machine; the containerized `portforge-api` build cannot
  resolve external hostnames. Not a v1.1-B code issue — verified
  environment-level. Worked around identically to v1.1-A: bare-process
  Central against the same real Postgres. Not "fixed," per explicit
  out-of-scope instruction.
- **Plaintext SSH passwords in the repo** — `scripts/deploy_remote.py`
  contains plaintext passwords for lenovoserver, tejaserver, and a
  MacBook, discovered incidentally while locating lenovoserver's address
  for deployment. Not used or reproduced anywhere in this work (SSH
  key-based auth was used instead, which already worked). Not modified —
  historical credential cleanup is explicitly out of scope for v1.1-B.
- **Two unfamiliar fleet hosts** — `PI-NODE-1` and a duplicate
  `lenovoserver` UUID entry were visible in Central's host list but were
  never created or touched by this session's work; noted, not
  investigated (out of scope).
- **The TOCTOU race is inherent, not a bug** — see §11. No future
  increment described in the v1.1 roadmap changes this; it is a property
  of any probe-then-act design over a network.
- **`unavailable` and `not_remote_capable` are visually similar but
  distinct** — the former means an attempt was made and failed or
  couldn't be attempted (e.g., offline host); the latter is the v1.0
  default meaning no attempt is relevant/possible for this candidate.
  Callers must not conflate the two when building any future UI over this
  field.
