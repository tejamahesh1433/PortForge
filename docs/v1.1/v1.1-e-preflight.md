## What changed

**`dashboard/lib/api/config.ts`**:

```diff
 export const PORTFORGE_API_URL: string =
-  process.env.NEXT_PUBLIC_PORTFORGE_API_URL ?? "http://127.0.0.1:58000";
+  typeof window === "undefined" && process.env.PORTFORGE_INTERNAL_API_URL
+    ? process.env.PORTFORGE_INTERNAL_API_URL

```

**`docker-compose.yml`** (`portforge-dashboard` service `environment:`):

```diff
-      - NEXT_PUBLIC_PORTFORGE_API_URL=http://127.0.0.1:${PORTFORGE_API_HOST_PORT:-58000}
+      - NEXT_PUBLIC_PORTFORGE_API_URL=http://localhost:${PORTFORGE_API_HOST_PORT:-58000}
+      - PORTFORGE_INTERNAL_API_URL=http://portforge-api:8000
```

## What this actually does

Adds a second, server-side-only API base URL
(`PORTFORGE_INTERNAL_API_URL=http://portforge-api:8000`, Docker's internal
service DNS name) used only when `typeof window === "undefined"` (i.e.,
code running in the dashboard container's own Node.js process, not a
browser). The existing `NEXT_PUBLIC_PORTFORGE_API_URL` (browser-facing,
`127.0.0.1`/`localhost` from the *host's* perspective) is unchanged in
purpose, just with its bare fallback literal changed from `127.0.0.1` to
`localhost`.

This is a real, technically sound fix for a real class of bug: if the
dashboard container's own server process ever calls Central directly
(server components, route handlers, middleware), `127.0.0.1` inside that
container resolves to the container itself, not the `portforge-api`
container — such a call would fail or hang. Using Docker Compose's service
DNS name (`portforge-api`) for server-side calls is the standard fix.
Whether this dashboard currently has any such server-side call path was
not verified as part of this preflight (see "Status" below) — every page
in this codebase is `"use client"` per v1.1-A through v1.1-D's own work,
so this fix may currently be defensive/unused rather than fixing an
observed failure.
