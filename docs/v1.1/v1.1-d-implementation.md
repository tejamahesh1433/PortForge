# v1.1-D Implementation: Dashboard Operational Visibility

Implements the scope of `docs/v1.1/roadmap.md`'s v1.1-D increment, grounded
in `docs/v1.1/dashboard-audit.md` (its P1 "no allocation visibility" finding
is the primary gap this increment closes) and
`docs/v1.1/v1.1-d-data-audit.md` (written first, per the task's own
instruction — see that document for the full A/B/C/D capability
classification this implementation follows).

## 1. Data-availability audit summary

See `docs/v1.1/v1.1-d-data-audit.md` for the full matrix. Headline
decisions: a new `GET /api/allocations` list endpoint was required
(Category C — no list endpoint existed); remote-probe evidence is computed
**live** at read time rather than a stored creation-time snapshot (avoids a
migration and avoids a permanently-stale flag); Host Compatibility required
a deliberate, user-approved reversal of a v1.1-A "never persisted" decision
(one nullable `hosts.protocol_version` column); workflow and config-mutation
state remain genuinely agent-local and are represented with a labeled note,
never fabricated.

## 2. New/changed routes

- `/allocations` (new) — list, filterable by host/project/status/search.
- `/allocations/[allocationId]` (new) — detail, release action.
- `/projects/[projectId]` — new "Allocations" tab (client-side, calls the
  same list endpoint filtered by project — no backend schema duplication).
- `/hosts/[hostId]` — Diagnostics tab gained two new cards (Protocol
  Compatibility, Remote Probe Capability).
- `/` (Overview) — new "Active allocations" metric card.

## 3. New/changed backend APIs

- **`GET /api/allocations`** (new) — `host_id`, `project`, `status`,
  `search`, `limit` (default 50, max 100), `offset`. Returns `Page<AllocationOut>`,
  deterministic ordering (`created_at DESC, id DESC`).
- **`AllocationEntryOut`** — additive fields `bind_address: Optional[str]`,
  `bind_probe: str` (live-computed).
- **`AllocationOut`** — additive field `request_id: Optional[str]`.
- **`HostOut`** — additive fields `protocol_version: Optional[int]`,
  `protocol_compatibility: str` (always recomputed live via the existing,
  unchanged `compatibility_service.evaluate_protocol_compatibility()`).
- **`HostDiagnosticsOut`** — additive field `probe_capability: str`
  (`"supported" | "unknown" | "unavailable_offline"`), computed only for
  single-host detail reads, never for the bulk list (avoids an N+1 on
  `GET /api/hosts`).
- **Migration `038acf539985_add_host_protocol_version.py`** — one nullable
  `Integer` column on `hosts`. See §5 for why.

No other endpoint contracts changed. `DELETE /api/allocations/{id}`
(release) was already exposed by Phase 8A — the dashboard just calls it.

## 4. Allocations UI

List (`app/allocations/page.tsx`): project, host (linked), bindings
(compact port chips), probe evidence (strongest-in-bundle badge), state,
request ID, created time, release action. URL-backed `host_id`/`status`/`q`
filters, `ActiveFilters` chips, reset. Mirrors the existing
`app/ports/page.tsx`/`app/reservations/page.tsx` patterns exactly — no new
table component, no new filter primitive.

Detail (`app/allocations/[allocationId]/page.tsx`): identity, host link,
project, request ID, created/released timestamps, bundle-level validation
snapshot, per-binding cards (port/protocol/bind address, purpose, live
probe evidence with its full explanation always visible as static text —
not only in a tooltip), an explicit statement that an allocation does not
prove a process is currently listening, and the workflow/config-mutation
honesty note (§9 below). A released allocation's empty bindings list is
explained, not left as an unexplained blank table (Phase 8A's known
"released allocation is a live join" limitation, carried from
`dashboard-audit.md`'s P2 list).

## 5. Probe evidence presentation

`components/status/bind-probe-badge.tsx` — one shared component for all 5
`bind_probe` values, used on the list, detail, and Project Detail's
Allocations tab. Every value has a full-sentence description shown as a
visible caption on the detail page (not only in the tooltip, per task
§19). The `verified_free` wording is the single most load-bearing piece of
copy in this increment — see §14 for its exact text and how it's verified.

## 6. Compatibility presentation

`components/status/host-compatibility-card.tsx` — `CompatibilityCard`
(Agent Version, Agent Protocol Version, Compatibility state) and
`ProbeCapabilityCard` (Supported / Unknown-not-yet-probed /
Unavailable-host-not-healthy), both on Host Detail's Diagnostics tab. Every
state has an explanatory caption; "unknown" is worded to explicitly state
it is *not* an error and *not* the same as "unsupported" — legacy agents
render honestly, never as broken.

## 7. Project detail improvements

New "Allocations" tab (`ProjectAllocationsTab`, inline in
`app/projects/[projectId]/page.tsx`) calls `useAllocations({project:
projectName})` directly — a drill-down link, not a duplicated table, per
task §9's explicit instruction. No backend schema change to
`ProjectDetailOut` was needed or made.

## 8. Workflow visibility decision

**Option B** (per `docs/v1.1/v1.1-d-data-audit.md`): a labeled, honest
note on Allocation Detail — *"Workflow and config-mutation state is local
to the project host"* — naming the real files
(`.portforge/workflows/`, `.portforge/mutations/`) and the real CLI
commands to inspect them (`portforge workflow status --request-id <id>`,
`portforge config status <mutation_id>`). No global workflow page, no
synchronization subsystem, nothing fabricated.

## 9. Config-mutation visibility decision

Same decision, same component, same reasoning as §8 — mutation records
are agent-local by the same architectural fact (Phase 8C's
`.portforge/mutations/<id>/record.json`, which can contain a project's
real `.env` values and must never be exposed to a browser even if it
could be read remotely). No remote filesystem browser, no arbitrary
file-read API, per task §11's explicit prohibition.

## 10. Overview changes

One new `MetricCard` ("Active allocations", linking to `/allocations`),
fetched via `useAllocations({status: "active", limit: 1})` (only the
`total` count is used — a bounded, cheap query, not fetching full rows to
render one number). Grid widened from 5 to 6 columns; no other Overview
change, per task §13's explicit "avoid a wall of cards" instruction.

## 11. Filter/search behavior

URL-backed (`host_id`, `status`, `q` query params), survives refresh and
back/forward navigation — physically verified (see §23).

## 12. Freshness behavior

No changes to `derive_health_state`/`FreshnessWarning` — both reused
unchanged. Host Detail's stale/offline states now additionally drive
`ProbeCapabilityCard`'s `unavailable_offline` state, so probe capability
is never presented as current for a host Central cannot currently vouch
for.

## 13. Error handling

Every touched page follows the existing `LoadingState`/`ErrorState`/
`EmptyState` convention. `ErrorState` renders Central's real error detail
(via `PortForgeApiError`/`PortForgeConnectionError`), never an
empty-success screen — verified both by automated tests
(`AllocationsPage error state` in `app/allocations/page.test.tsx`) and
physically (§24).

## 14. TOCTOU wording — the mandatory check (task §32)

`getBindProbeMeta("verified_free").description`:

> "Verified free on the target host at probe time. This is not a
> guarantee the port is currently free -- an unmanaged process on that
> host can still bind it afterward."

Verified by `components/status/bind-probe-badge.test.tsx`'s dedicated
`describe` block, which asserts the string contains the approved phrase,
explicitly disclaims a current/permanent guarantee, and never contains
"reserved by probe" or "currently guaranteed". This description is shown
as static, always-visible text on Allocation Detail (§4), not only in a
tooltip.

## 17. Docker deployment note (incidental, not new architecture)

Physical acceptance was ultimately performed against the real
`docker compose`-deployed `portforge-dashboard` and `portforge-api`
containers on port 3000/58000 (at the user's explicit request), not the
ad-hoc dev-server workaround used earlier in the v1.1 series. Getting
there required fixing two real, pre-existing problems, neither part of
v1.1-D's own code:

1. **A stray, uncommitted, broken edit to `dashboard/Dockerfile`** (base
   image changed to `node:22-slim` but the Alpine-only `apk` command was
   left in place) — reverted to the last committed, coherent version.
2. **Docker Desktop's WSL2 VM had no working DNS at all** (`/etc/resolv.conf`
   missing entirely inside the `docker-desktop` WSL distro) — resolved
   with `wsl --shutdown` (explicit user approval), which forced Docker
   Desktop to reinitialize its network stack.

Neither of these is a v1.1-D code change, and neither was "fixed" in the
sense of altering PortForge's production architecture — they were
environment-level repairs to this dev machine's Docker Desktop
installation, explicitly authorized by the user in real time.

## 18. Known limitations found during physical acceptance

- **Central-unavailable time-to-error can be very slow.** While Central
  was stopped, both an already-loaded page's in-flight request and a
  **fresh** page load stayed in the `LoadingState`/`"Connecting…"` state
  for 20+ seconds without transitioning to `ErrorState`, even though
  `curl` against the same stopped port failed in ~2 seconds. The
  ErrorState rendering logic itself is correct and verified (automated
  tests mock `isError: true` directly and confirm correct rendering) — the
  gap is that `fetch()` in this browser, against this specific
  Windows/Docker-Desktop port-teardown behavior, does not reject quickly.
  The core requirement (never show fake empty/zero data during an outage)
  held throughout — the dashboard never displayed a false "0 hosts"/"0
  allocations" result — but a long stuck-loading period is a real UX gap
  worth a future look, likely via a client-side fetch timeout
  (`AbortSignal.timeout(...)`) rather than relying solely on TanStack
  Query's retry/backoff. Not fixed in this increment (would be scope
  creep beyond "make existing capabilities visible"), documented for a
  future pass.
- **Project-detail tab wrapping — found again, fixed.** The
  `dashboard-audit.md`-documented issue was still present at 768px;
  fixed with a scoped, one-line change (`flex-wrap` → `overflow-x-auto`)
  to `app/projects/[projectId]/page.tsx`'s own `TabsList` usage only —
  the shared `components/ui/tabs.tsx` primitive was not touched.
  `docs/v1.1/dashboard-audit.md` is updated to mark this P1 item resolved.
- **Real, incidental credential-architecture bug found and worked
  around** (agent-side, unrelated to the dashboard): the agent has two
  separate credential stores — `central.json`'s `token` field, written by
  `portforge central enroll`, and `credentials.json`, read by the
  always-on daemon (`portforge agent run`) via `credentials.load_credential()`.
  `central enroll` does not update `credentials.json`, so a host enrolled
  only via `central enroll` fails every daemon heartbeat with "Invalid or
  revoked agent credential" until re-enrolled via the separate
  `portforge agent enroll --server <url> --token <token>` command. Worked
  around during physical acceptance by using the correct command; not
  fixed in the agent codebase (out of scope for a dashboard increment,
  and explicitly not one of the debts this increment was scoped to
  touch — see task §38).
- Carried forward, unchanged, per task §38: Docker Desktop DNS
  characteristics on this dev machine, `scripts/deploy_remote.py`'s
  plaintext credentials, `PI-NODE-1`/duplicate-lenovoserver-UUID fleet
  identity questions, `cli_agent.py`'s fake timestamp, install/upgrade
  tooling, Phase 8D evidence.
- No live-cluster NodePort discovery (carried from v1.1-C) — irrelevant
  to this increment's scope but noted for completeness since Kubernetes
  visibility was explicitly considered and correctly left unaddressed
  (task §12 — no distinguishing metadata reaches Central for a
  Kubernetes-origin allocation, so none is shown).
