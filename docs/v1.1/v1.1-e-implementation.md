# v1.1-E: Installation, Service Setup & Safe Upgrade

## Summary

This increment made PortForge installation reproducible by fixing documentation that had never actually worked
(verified against the real CLI, not assumed), closing two real gaps found during the audit (a dual
credential-store bug and a missing Linux `linger` step), implementing the one small CLI command
`docs/security.md` had always claimed existed but didn't, writing idempotent install scripts, and physically
proving a v1.0.0-schema-to-v1.1 upgrade preserves host identity and data end to end.

## What was found broken (docs/v1.1/cli-audit.md has the full matrix)

- `docs/installation.md` referenced a nonexistent `portforge-agent` binary and a nonexistent `portforge enroll
  --central` flag shape, and claimed the backend runs on port 8000 (that's the container-internal port; the
  published host port defaults to 58000). Following it literally could not stand up PortForge.
- `docs/security.md` and `docs/quickstart.md` referenced `portforge central generate-token`, which did not
  exist as a CLI command -- only an unexposed backend endpoint (`POST /agent/enrollment-tokens`, admin-only)
  did.
- Two real installation-correctness bugs, found by reading the actual source rather than assuming:
  1. **Dual credential-store bug**: `central enroll` wrote only `central.json`'s embedded token; the always-on
     daemon (what every installed native service actually runs) reads only `credentials.json`. A host enrolled
     via `central enroll` alone would authenticate for one-off `central sync`/`status` calls but the installed
     service would silently fail every heartbeat with "Invalid or revoked agent credential" -- exactly what was
     hit during v1.1-D's physical fleet reconnection work.
  2. **Missing Linux linger step**: `agent service install` never ran `loginctl enable-linger`, so a headless
     host's `systemctl --user` service would stop at logout and never restart at boot. Confirmed real via SSH
     (`lenovoserver` already had `Linger=yes` set manually, outside PortForge's own automation).

## What changed

### Code
- `agent/portforge_agent/credentials.py` -- `load_credential()` now falls back to `central.json`'s legacy
  token when `credentials.json` has none, and self-heals by writing it into `credentials.json` on first read.
  Isolated test paths (`path=` override) deliberately never fall back to the real machine's `central.json`.
- `agent/portforge_agent/central_sync.py` -- `enroll()` now writes to both `central.json` and
  `credentials.json`, so either enrollment command produces a fully-working installation.
- `agent/portforge_agent/service_ops.py` -- Linux `install()` now calls a new `_ensure_linger()` after the
  systemd unit is enabled. Best-effort: a `loginctl enable-linger` failure (e.g. a locked-down system) is
  folded into the result's `detail` as an informational note and never fails the install, matching the existing
  Windows elevation-detection philosophy (detect and explain, never silently require elevation).
- `agent/portforge_agent/central_client.py` -- new `generate_enrollment_token()`, a thin wrapper around the
  backend's existing admin-only `POST /agent/enrollment-tokens`.
- `agent/portforge_agent/cli.py` -- new `portforge central generate-token --url URL [--admin-token TOK]
  [--label] [--ttl-hours]` command. Resolves the admin bootstrap token from `--admin-token` or the
  `PORTFORGE_ADMIN_BOOTSTRAP_TOKEN` env var (env var preferred, to avoid shell-history exposure); never logs
  it; prints the minted enrollment token exactly once, matching the backend's own one-time-reveal semantics.
  This closes the exact gap `docs/security.md` had always assumed was already implemented -- no new auth
  mechanism, still requires the real admin bootstrap token.

### Tests (agent suite: 697 passed, 2 skipped -- up from 690/2 at v1.1-D)
- `agent/tests/test_credentials.py` (new, 10 tests) -- round-trip, malformed JSON, legacy fallback + self-heal,
  isolation guarantees.
- `agent/tests/test_service_ops.py` (+3 tests) -- linger already-enabled (skip), newly-enabled, enable-failure
  treated as non-fatal.
- `agent/tests/test_cli_central_generate_token.py` (new, 7 tests) -- admin-token resolution (flag/env/missing),
  JSON purity, human output shows the token once with a usage hint, failure path, label/ttl pass-through.

### Documentation
- `docs/installation.md` -- rewritten to match the real CLI: correct package/script name, correct enrollment
  commands (`central generate-token` + `agent enroll`), correct ports (58000 host / 8000 container), explicit
  `PORTFORGE_ADMIN_BOOTSTRAP_TOKEN` requirement, `doctor` as the final verification step, and the three
  supported installation models.
- `docs/quickstart.md`, `docs/cli.md`, `docs/security.md` -- corrected the same command-shape errors.
- `docs/v1.1/cli-audit.md` (new) -- the full COMMAND/EXISTS?/PURPOSE/INSTALLATION-RELEVANCE/PLATFORM matrix,
  captured directly from real `--help` output, plus the installation-model definitions.
- `docs/v1.1/upgrade.md` (new) -- the agent and Central upgrade procedures, version-compatibility notes, and
  rollback guidance (app rollback vs. DB rollback are explicitly not equivalent; `alembic downgrade` against
  live data is explicitly discouraged in favor of a pre-upgrade volume backup).
- `scripts/install.ps1` / `scripts/install.sh` (new) -- idempotent installers (pip install -e, `agent service
  install`, optional enrollment via `-CentralUrl`/`-EnrollmentToken` or `--central-url`/`--enrollment-token`,
  `agent service start`, `doctor`). No hardcoded machine-specific paths, credentials, or usernames.

## Physical validation performed this increment

1. **CLI audit**: every command in `docs/v1.1/cli-audit.md` invoked directly (`--help`, and several
   end-to-end) against the real CLI, not inferred from source reading alone.
2. **`central generate-token` end-to-end**: minted a real enrollment token against the live `portforge-api`
   container using the real (dev-labeled) admin bootstrap token; both success and wrong-admin-token failure
   paths confirmed via real HTTP round-trips.
3. **Mandatory v1.0.0 -> v1.1 upgrade test**: a disposable Postgres container (`postgres:16-alpine`, port
   55499, destroyed afterward) was seeded via a `git worktree` checkout of the real `v1.0.0` tag running its
   own backend code -- not a simulated schema. A host was enrolled with a controlled UUID
   (`99999999-8888-7777-6666-555555555555`), a heartbeat was sent, and a reservation was created, all through
   v1.0.0's real API. `alembic upgrade head` was then run against the *same* database using the current
   (v1.1-E) migration chain (`add_host_probes` -> `add_host_protocol_version`). The current backend was started
   against the upgraded database and confirmed: identical host UUID, identical `first_seen` timestamp,
   identical reservation (same id, same fields), and the new `protocol_version` column correctly `null`/
   `protocol_compatibility: "unknown"` for the pre-upgrade host (not a fabricated value). Credential
   continuity was confirmed by code inspection: no v1.1 commit touched `auth.py`, `agent_credential.py`, or
   `agent_repository.py`, and no migration in the chain alters the `agent_credentials` table, so the
   v1.0.0-issued bearer credential is unaffected by construction. Disposable Postgres container and git
   worktree were both torn down afterward.
4. **Documentation-executability test (Sec31, mandatory)**: a genuinely fresh Python virtualenv (not this
   session's environment) followed `docs/installation.md`'s Host Agent Setup + Host Enrollment sections
   literally -- `pip install -e ./agent`, `portforge --help`, `portforge central generate-token --url
   http://localhost:58000`, `portforge agent enroll --server ... --token ...`, `portforge doctor --url ...` --
   against the real running Central, with `LOCALAPPDATA` redirected to an isolated temp directory so the test
   could not clobber this machine's real enrollment/host-identity state. Every command in the doc worked
   exactly as written; `doctor` reported all-PASS. Confirmed both `central.json` and `credentials.json` were
   written (the dual-credential-store fix verified working through the real CLI path, not just unit tests).
   The disposable venv, its isolated data directory, and the test host record + credential it created on the
   real Central (`fa602a08-...`, a duplicate "NTMKEYA" entry) were all cleaned up afterward -- confirmed via
   direct `hosts` table query that the fleet is back to exactly its real 4 hosts.
5. **NTMKEYA (this machine) service reinstall**: `pip install -e ./agent` re-run confirmed idempotent (no
   errors, `doctor` all-PASS afterward, host UUID `f90db087-...` unchanged). `portforge agent service install`

## Deliberately not attempted this increment (see task Sec37, Sec44)

- No `portforge upgrade` self-updater command -- `docs/v1.1/upgrade.md` documents the explicit, boring
  sequence (`git pull` + `pip install -e --upgrade` + `agent service install` + `doctor`) as the supported
  path instead, per the task's own preference for reliability over magic.
- No GitHub Release, tag push, PyPI/Homebrew/winget publishing, or license work -- this increment is about
  reproducible installation from source, not public distribution.
- No changes to `scripts/deploy_remote.py`, the fleet's stale/uncommitted remote checkouts, the pre-existing
  duplicate Lenovo UUID, or Docker Desktop's WSL2 DNS behavior -- all pre-existing carried debt explicitly out
  of this increment's scope.
- `dashboard/lib/api/config.ts` and `docker-compose.yml`'s uncommitted working-tree changes remain untouched,
  exactly as found -- see `docs/v1.1/v1.1-e-preflight.md` for the provenance investigation (inconclusive;
  preserved rather than guessed at, per explicit task instruction).
- Full fleet-wide physical redeploy/re-verification of this increment's Linux/macOS service-layer code (items
  5-6 above) -- constrained by the pre-existing messy remote-checkout state, itself carried debt. What *was*
  independently, physically verified: the credential/enrollment fix (end-to-end, via the real CLI, in item 4
  above) and the DB migration/upgrade path (item 3), which are the two changes with the highest blast radius.
