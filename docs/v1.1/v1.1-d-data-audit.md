# v1.1-D Data-Availability Audit

Written before any dashboard/backend code changed for this increment, per
the task's own instruction. Classifies every desired v1.1-D UI capability
against what Central actually knows today (`backend/app/models/`,
`backend/app/schemas/`, `backend/app/api/`), inspected directly — not
assumed from `docs/v1.1/dashboard-audit.md`'s earlier, code-free sketch.

Categories: **A** already available from Central · **B** derivable safely
from existing Central data · **C** requires a small additive read-only
Central API · **D** fundamentally agent-local, unavailable to Central.

## Allocations (list + detail)

**C.** `backend/app/api/allocations.py` has `POST`, `GET /{id}`, `DELETE
/{id}` only — no list endpoint. Adding `GET /api/allocations` (filtered,
paginated, mirroring `GET /api/reservations`'s existing convention exactly)
is the only way to satisfy task §2. `AllocationRepository` gets one new
`list()` method; no new table.

## Allocation release

**A.** `DELETE /api/allocations/{id}` (`allocation_service.release_allocation`)
already exists, is idempotent, and uses the real allocation-release
contract (deletes the bundle's reservations, marks the allocation
`released`). The dashboard only needs to call it — no backend change.

## Remote-probe evidence on allocations

**B, with a deliberate design choice.** v1.1-B's `HostProbe` rows are
real, queryable Central data (`probe_service.get_probe_evidence`). The
allocation-creation code path (`allocation_service.create_allocation`)
computes a bundle-level `bind_probe` at the moment of creation but **never
persists it** — `AllocationValidationOut.bind_probe` defaults back to
`"not_remote_capable"` on every subsequent `GET`. Two ways to close this:

1. Persist the creation-time `bind_probe` snapshot on the `Allocation` row
   (another migration).
2. Compute evidence **live**, per allocated binding, at every read
   (list/detail) by querying `HostProbe` for that exact
   `(host_id, port, protocol)` at render time.

**Chose (2), no migration.** A stored creation-time snapshot would become
permanently stale/misleading the moment the probe's 120s TTL elapses —
exactly the kind of "verified_free presented as a permanent guarantee"
the task's §5/§32 explicitly warn against. Live evidence is strictly more
honest: it always reflects the CURRENT freshness state of whatever
evidence exists for that binding, not what was true at creation. This adds
`bind_probe: str` and `bind_address: Optional[str]` to
`AllocationEntryOut` (both additive, defaulted, non-breaking), computed via
one batched query per list/detail call (see §22 performance note in the
implementation doc) rather than one query per entry.

## Host protocol compatibility

**C, with an explicit reversal of a prior decision — user-approved.**
`backend/app/services/compatibility_service.py`'s own docstring says
protocol-version compatibility is "Deliberately NOT persisted anywhere —
no Host column, no migration" (a real v1.1-A design choice: the
evaluation is a pure function of a single request, computed fresh and
discarded). This means Central has **zero memory** of a host's
last-reported `protocol_version` between requests — `GET /api/hosts`/
`GET /api/hosts/{id}`, called later from an unrelated dashboard request,
cannot know it no matter how it's queried.

Satisfying task §7 (a named, priority-5 requirement: "Expose v1.1-A
protocol compatibility in Host detail") honestly requires this to survive
between requests. Presented to the user as an explicit architectural
conflict before proceeding; the user chose to add the minimal migration
(one nullable `hosts.protocol_version` column, populated on every
heartbeat/enroll, **compatibility itself still computed live** via the
existing unchanged `evaluate_protocol_compatibility()` — only the raw
reported integer is stored, never a precomputed verdict that could go
stale if Central's own `PROTOCOL_VERSION` ever changes). See
`docs/v1.1/v1.1-d-implementation.md` §5 for the exact migration.

## Host probe capability

**B.** No new persistence. Central can honestly infer "this host has
answered at least one remote probe" by checking for ANY `HostProbe` row
for that host with `status IN ('COMPLETED', 'FAILED')` — proof the
agent's remote-probe code path actually ran. Absence of such a row is
**not** proof of incapability (the host may simply never have been asked)
— worded in the UI as "Unknown / not yet probed", never "Unsupported",
unless the host is legacy enough to predate v1.1-B by version comparison.
Offline/stale hosts get their own honest state regardless of probe
history (task §8's explicit example list). No new endpoint needed beyond
the allocation list's existing evidence machinery, reused per-host.

## Project ↔ Allocation relationships

**B.** No backend schema change. `ProjectDetailOut` already aggregates
ports/reservations/conflicts/activity server-side; duplicating that same
join for allocations would be schema churn for data the new `GET
/api/allocations?project=<name>` endpoint (added for the Allocations page
itself) already answers directly. Project detail links to a
project-filtered Allocations view client-side instead — "add links/
drill-down rather than duplicating entire tables," per the task's own
instruction.

## Phase 8D workflow state

**D.** `agent/portforge_agent/workflow.py`'s `WorkflowRecord` persists at
`<project_root>/.portforge/workflows/<sha256(request_id)>/record.json` —
literally a file on the coding agent's own project directory on whichever
host ran `portforge workflow apply`. Nothing about it is ever transmitted
to Central; Central has no endpoint, no table, no awareness of workflow
records existing at all. This is not a missing API — it is data that
structurally never leaves the host filesystem. Building a "global workflow
page" would require either a new synchronization subsystem (explicitly
prohibited: "Do not introduce a large synchronization subsystem merely to
populate a dashboard") or fabricating data. **Decision: option B** — a
clearly-labeled "Workflow state is local to the project host" note,
pointing at `portforge workflow status --request-id <id>` as the real
source of truth, placed on Project Detail. No fabricated workflow page.

## Phase 8C config mutation state

**D.** Same reasoning, same file-local structure
(`<project_root>/.portforge/mutations/<mutation_id>/record.json`,
including config plan/apply/rollback status, per-file SHA-256 hashes, and
`new_content` — the last of which must never be exposed to a browser even
if it COULD be read remotely, since it can contain a project's real
`.env` values). **Decision: option B**, same as workflow — a labeled note
pointing at `portforge config status <mutation_id>`. No remote filesystem
browser, no arbitrary file-read API (both explicitly prohibited by task
§11).

## Kubernetes-specific allocation identity

**D.** v1.1-C's Kubernetes config integration writes `hostPort`/`nodePort`
values into a project's own YAML files entirely client-side
(`agent/portforge_agent/k8s_editor.py`) — the allocation Central records
for that binding is indistinguishable from any other allocation; no field
anywhere marks "this port was written into a Kubernetes manifest." Task
§12 explicitly forbids inferring Kubernetes involvement from port ranges.
**Decision: no Kubernetes-specific dashboard treatment in v1.1-D** — an
allocation used for a Kubernetes `hostPort`/`nodePort` mapping is shown
exactly like any other allocation, honestly, because that is all Central
actually knows about it.
