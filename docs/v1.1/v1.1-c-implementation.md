# v1.1-C Implementation: Safe Kubernetes Config Integration

Implements the scope of `docs/v1.1/roadmap.md`'s v1.1-C increment, grounded
in `docs/v1.1/kubernetes-design.md` (two corrections added to that doc as
part of this implementation — see its final section, and §14 below). Reuses
Phase 8C's entire safe config-mutation architecture unchanged; Kubernetes is
a third target-file kind alongside dotenv and Compose, not a second engine.

## 1. Scope

Local single-node development clusters only (`kind`, Docker Desktop
Kubernetes) — never production/multi-node clusters. PortForge may own only
two fields:

- container `hostPort` (binds directly on the node's own network
  namespace — a real host-network resource)
- Service `nodePort` (opens on every node; in a single-node cluster "every
  node" reduces to "the one dev machine")

`containerPort`, Service `port`, and `targetPort` are cluster-internal
routing values PortForge never writes, never validates against Central's
reservation table, and never treats as a conflict source — they are used
only as immutable match keys.

## 2. Manifest schema

Additive, third `config:` key (`kubernetes`, alongside the existing
`dotenv`/`compose`) — a manifest with no `kubernetes` key validates exactly
as before (verified:
`test_existing_manifest_without_kubernetes_key_still_valid`,
`test_existing_dotenv_only_manifest_gets_empty_kubernetes_list`).

```yaml
config:
  kubernetes:
    - file: k8s/app.yaml
      hostPorts:
        - kind: Deployment          # Deployment | StatefulSet
          name: frontend             # metadata.name
          namespace: dev             # optional, disambiguates duplicate names
          container: web             # container name in the Pod template
          containerPort: 3000        # match key -- never itself changed
          protocol: tcp              # default tcp
          allocation: frontend_port  # a ports.<name> request from this manifest
      nodePorts:
        - name: api-svc              # Service metadata.name
          namespace: dev
          servicePort: 8080          # Service's own `port` field -- NOT targetPort
          protocol: tcp
          allocation: api_nodeport
```

Every field is explicit — no guessing from service/container names, no
scanning-and-rewriting every port-looking integer. Unknown fields rejected.
Bounded: `MAX_CONFIG_FILES_PER_KIND` (10, shared with dotenv/compose),
`MAX_HOSTPORTS_PER_KUBERNETES_FILE`/`MAX_NODEPORTS_PER_KUBERNETES_FILE` (50
each). Duplicate mappings targeting the identical `(kind, namespace, name,
container, containerPort)` or `(namespace, name, servicePort)` location are
rejected at validation time (`CONFIG_MAPPING_INVALID`), before ever reaching
the editor.

## 3. Supported resource kinds

`Deployment` and `StatefulSet` for `hostPort` (both navigate identically to
`spec.template.spec.containers[]`), `Service` for `nodePort`. `DaemonSet`/
`Pod` were in the original design sketch's kind list but excluded here per
the task's own narrower approved scope ("support only resource kinds
required... do not add broad support unnecessarily") — noted as a possible
future addition, not implemented.

## 4. hostPort implementation

`agent/portforge_agent/k8s_editor.py::apply_host_port()` — locates the
resource by `(kind, name, namespace?)`, then the named container in
`spec.template.spec.containers[]`, then the `ports[]` entry matching
`(containerPort, protocol)`, then sets ONLY that entry's `hostPort`. Zero,
one, or ambiguous matches at every stage fail safely with a specific error
code (`KUBERNETES_RESOURCE_NOT_FOUND`/`_AMBIGUOUS`,
`KUBERNETES_CONTAINER_NOT_FOUND`/`_AMBIGUOUS`,
`KUBERNETES_PORT_NOT_FOUND`/`_AMBIGUOUS`) — never "the first thing that
looks close."

## 5. nodePort implementation

`k8s_editor.py::apply_node_port()` — locates the `Service` by
`(name, namespace?)`, validates `spec.type` is `NodePort` or `LoadBalancer`
(a `ClusterIP`/missing-type Service fails with
`KUBERNETES_SERVICE_TYPE_UNSUPPORTED` — PortForge never silently converts a
Service's type), then the `spec.ports[]` entry matching `(port, protocol)`,
then sets ONLY that entry's `nodePort`.

**NodePort range validation** (task §5): PortForge has no live-cluster
access during config plan/apply (see §21 in the design doc — deliberate),
so it cannot authoritatively discover a cluster's configured NodePort
range. `config_manager.py::_plan_kubernetes_file` validates the resolved
allocation's port against the documented supported-local-cluster
assumption, `k8s_editor.DEFAULT_NODEPORT_RANGE = (30000, 32767)` (kind's
and Docker Desktop Kubernetes' shared default), failing the plan with
`KUBERNETES_NODEPORT_OUT_OF_RANGE` rather than writing a value the cluster
would then reject. The `ports.<name>.preferred` field is how a manifest
author puts the corresponding allocation request into that range.

## 6. Fields intentionally never touched

`containerPort`, container `name`, container `protocol`, Service `port`,
Service `targetPort`, Service `type` — verified directly:
`test_containerport_and_container_name_never_mutated`,
`test_service_port_and_target_port_never_mutated`, and the physical
acceptance evidence in §15 below.

## 7. Multi-document YAML handling

`k8s_editor.py::load_kubernetes_documents()`/`dump_kubernetes_documents()`
use `ruamel.yaml`'s round-trip mode (`typ="rt"`) via `load_all`/`dump_all`
— the same round-trip settings already proven for Compose
(`indent(mapping=2, sequence=4, offset=2)`, `preserve_quotes`), applied
per-document. Comments, document boundaries, and unrelated documents in the
same file are preserved and untouched — verified both automatically
(`test_comments_and_unrelated_document_preserved_after_mutation`,
`test_unrelated_third_document_untouched`) and physically (§15).
`typ="rt"` never constructs arbitrary Python objects from YAML tags — the
same safety property `compose_editor.py` and `manifest.py`'s
`yaml.safe_load()` already rely on. Bounded: `MAX_KUBERNETES_FILE_BYTES`
(2 MiB) and `MAX_KUBERNETES_DOCUMENTS` (50), both enforced before parsing.

## 8. Mutation architecture (Phase 8C, reused unchanged)

`config_manager.py::_plan_kubernetes_file()` is a third per-kind branch
inside the SAME `build_plan()`/`apply_mutation()`/`rollback_mutation()`/
`get_status()` orchestration Compose and dotenv already use — no second
mutation framework. A Kubernetes file's `PlannedFile.kind = "kubernetes"`
flows through the exact same generic mutation-record persistence,
SHA-256 preconditioning, atomic write, and backup/restore code paths.

## 9. Plan / apply / status / rollback behavior

- **Plan**: loads the current file, computes every intended change,
  persists a mutation record, **never writes the target file** — verified
  (`test_kubernetes_plan_is_non_mutating`, byte-identical + mtime
  unchanged).
- **Apply**: recomputes SHA-256 immediately before write; if the file
  changed since plan, refuses (`CONFIG_CHANGED_SINCE_PLAN`) rather than
  overwriting external edits (`test_kubernetes_external_edit_before_apply_blocks_apply`).
  Idempotent — a second `apply` of an already-`APPLIED` mutation does not
  rewrite the file (`test_kubernetes_apply_is_idempotent_no_duplicate_rewrite`,
  mtime unchanged).
- **Rollback**: recomputes SHA-256ing immediately before restore; refuses
  on a post-apply external edit
  (`test_kubernetes_external_edit_before_rollback_blocks_rollback`).
  Restores the exact original bytes — verified via SHA-256 equality
  before/after (`test_kubernetes_full_apply_rollback_cycle_exact_bytes`)
  and physically (§15). Never releases the allocation — config rollback
  and allocation release remain two independent actions
  (`test_kubernetes_allocation_remains_active_after_config_rollback`).

## 10. External-edit protection

Both directions tested and confirmed: an edit between plan and apply blocks
apply; an edit between apply and rollback blocks rollback. Neither
destroys the external edit — the file is left exactly as the external
edit left it, not overwritten with either the old or new PortForge content.

## 11. Combined-config compensation

A project mixing `dotenv` + `kubernetes` mappings applies/rolls back both
files together, atomically. A controlled failure writing the Kubernetes
file after the dotenv file was already written restores the dotenv file to
its original bytes — no partial config state survives
(`test_combined_config_failure_in_kubernetes_restores_earlier_dotenv_write`).
`workflow apply`'s own compensation (release a newly-created allocation,
roll back an applied mutation) was verified end-to-end too
(`test_workflow_kubernetes_missing_target_fails_and_compensates`).

## 12. Workflow integration

No new `portforge kubernetes ...` command. `workflow prepare`/`apply`/
`status` handle Kubernetes mappings exactly like dotenv/Compose ones — a
coding agent's workflow is identical regardless of config target kind
(`workflow.py`'s `_hash_manifest_for_workflow`, `prepare_workflow`'s
`config_files` listing, and `apply_workflow`'s `has_config` check all
extended additively). JSON output stays pure JSON, no progress banners
(`test_workflow_json_output_pure_json_with_kubernetes_config`).

## 13. Path / security validation

`resolve_within_root()` reused unchanged — `../` escape and symlink escape
both fail exactly as they do for dotenv/Compose
(`test_kubernetes_path_outside_project_rejected`,
`test_kubernetes_symlink_escape_rejected`). No arbitrary YAML command
execution (`typ="rt"` never executes Python constructors). No secret
leakage — `config status`/`plan` output never includes Kubernetes YAML
content beyond the specific changed fields
(`test_kubernetes_status_never_leaks_secrets`). No `kubectl`/cluster
invocation exists anywhere in PortForge's own code — task §21/§24 make
clear that `kubectl apply --dry-run=client`/`kubectl apply` are
ACCEPTANCE-HARNESS steps, not PortForge behavior, so no such subprocess
call was added to the codebase at all.

## 14. Allocation ownership validation

`verify_allocation_ownership()` (unchanged Phase 8C function) now also
collects Kubernetes-referenced allocation names into its `referenced` set
— a Kubernetes mapping referencing an allocation-request name that isn't
actually in the manifest's `ports:` fails exactly like a dotenv/Compose one
would (`CONFIG_MAPPING_INVALID`). Project/host mismatch checks are
unchanged and apply identically (`test_kubernetes_ownership_project_mismatch`,
`test_kubernetes_ownership_host_mismatch`).

## 15. Physical acceptance (real `kind` cluster on workstation)

`kind` was not pre-installed on this machine — installed the standard
`kind.exe` binary (v0.27.0) with the user's explicit approval, into an
already-PATH user-writable directory. A disposable cluster
(`portforge-v11c-test`) was created, exercised, and fully deleted.

**Real Docker Desktop DNS issue encountered again** (same class as
v1.1-A/B, not fixed here): the kind node container inherited the same
broken outbound DNS resolution, so `crictl pull` inside the node timed out.
Worked around WITHOUT touching Docker Desktop settings: pulled `nginx` on
the host (where DNS works), then hit a SEPARATE, unrelated bug —
`kind load docker-image`/`kind load image-archive` both failed with
`ctr: rpc error: ... content digest ... not found`, traced to Docker
Desktop's containerd-backed image store producing a multi-layer manifest
export `ctr images import` couldn't fully resolve. Worked around by
flattening the image to a single layer (`docker export`/`docker import`,
with an explicit `command:` in the Pod spec since flattening loses the
original image's `CMD`/`ENTRYPOINT` metadata), then `kind load
docker-image` succeeded on the flattened image.

**Project**: `frontend` Deployment (container `web`, `containerPort: 80`,
mapped to allocation `frontend_host`), `api` Deployment (unrelated —
proves the multi-document editor only touches what's mapped), `api-svc`
Service (`type: NodePort`, `port: 80`/`targetPort: 80`, mapped to
allocation `api_nodeport` with `preferred: 30180`).

**Full command flow demonstrated**: `project validate` → `project plan
--json` (purpose-range preview, does not reflect `preferred_port` — that's
pre-existing Phase 8B behavior, `preferred_port` only applies at real
allocation time) → `project allocate --json` (real `POST /api/allocations`,
returned `frontend_host: 3001`, `api_nodeport: 30180` — the preferred value,
honored exactly) → `config plan --json` (non-mutating, showed both changes
correctly: `hostPort` 3001, `nodePort` 30180) → `config apply --json`
(wrote the file) → independent inspection of the raw YAML.

**Proven directly by inspection**: `hostPort: 3001` inserted on `frontend`,
`nodePort: 30180` inserted on `api-svc`, `containerPort: 80`/`port: 80`/
`targetPort: 80` byte-identical to before, the unrelated `api` Deployment
document completely untouched (no `hostPort` added).

**`kubectl apply --dry-run=client`**: valid (acceptance harness step, not
PortForge behavior). **Real `kubectl apply`**: both Deployments and the
Service created successfully; both Pods reached `Ready` within seconds;
`kubectl get svc api-svc` showed `80:30180/TCP` — Kubernetes itself
accepted the exact nodePort value PortForge wrote.

**The critical honesty finding (§25/§26)**: `curl` from *inside* the kind
node container reached both `http://127.0.0.1:3001` (hostPort) and
`http://127.0.0.1:30180` (nodePort) with `HTTP 200` — proving Kubernetes
itself correctly enacted both bindings exactly as PortForge intended. But
`curl` from the *real Windows host* to `127.0.0.1:3001` and
`127.0.0.1:30180` both failed (`exit 7`, connection refused), and
`docker inspect` on the node container confirmed only `6443/tcp` (the API
server) was ever published to the Windows host. This is `kind`'s own
default behavior — `kind create cluster` with no `extraPortMappings` in
its cluster config only publishes the API server port. **PortForge's job
(write correct YAML, which Kubernetes correctly honors) is proven
complete and correct; genuine Windows-host reachability for a `kind`
cluster additionally requires the cluster operator to configure
`extraPortMappings` matching PortForge's allocated port — a cluster-level
decision outside PortForge's stated scope (PortForge writes files, never
touches the cluster).** This is documented here and in
`docs/v1.1/kubernetes-design.md`'s corrections section, not silently
absorbed into a false "it works" claim. Docker Desktop's built-in
Kubernetes (the design doc's other named target) was not available to
compare directly in this session — noted as unverified, not claimed either
way.

**Occupied-port safety** (§30, hostPort): a real listener was placed on
port 3100 on workstation. A first allocation attempt with `preferred_port:
3100` queued a probe (fire-and-forget, v1.1-B pattern) and, with no
evidence yet, returned 3100 anyway — the SAME honest behavior already
established and accepted in v1.1-B, not a v1.1-C regression (v1.1-C never
changes allocation-time port selection, only writes whatever
`allocation_service` already decided into YAML afterward). workstation's real
always-on agent (`PortForge Agent` Task Scheduler task, confirmed
`Running`) answered the probe within seconds
(`COMPLETED, result_available=False`). A second attempt, while that
evidence was still fresh, correctly avoided port 3100 and returned 3002
instead. Listener and allocations cleaned up.

**NodePort occupied-port distinction** (§30): PortForge has no
authoritative way to check whether a specific NodePort is already in use
*inside* a live cluster (that would require live cluster access, out of
scope per §21). It does not pretend to — the range-validation check
(§5 above) is the only NodePort-specific guard, and an actual in-cluster
NodePort collision would surface as a `kubectl apply` failure, not
something PortForge claims to catch. This is a documented limitation, not
a gap PortForge silently papers over.

**Multi-document** (§27): the unrelated `api` Deployment document, present
in the same file as the two mapped resources, was confirmed completely
unchanged after apply (no `hostPort` field added to it) — proven both by
inspection and by the automated round-trip tests in §7.

## 17. Known limitations

- **Windows-host reachability for `kind`** — see §15's honesty finding.
  Requires cluster-operator-configured `extraPortMappings`, outside
  PortForge's scope.
- **No live-cluster NodePort discovery** — the 30000-32767 range check is
  a documented assumption (kind's and Docker Desktop Kubernetes' shared
  default), not authoritative verification against a specific cluster's
  actual configured range.
- **Docker Desktop's built-in Kubernetes was not physically compared** —
  only `kind` was available and tested in this session.
- **`DaemonSet`/`Pod` hostPort mapping not implemented** — narrower scope
  than the original design sketch's kind list, per the task's explicit
  "do not add broad support unnecessarily." Could be added later if a
  concrete need arises.
- **Missing `containerPort`/`servicePort` entries fail rather than being
  invented** — a deliberate divergence from Compose's own
  append-if-missing behavior; see `docs/v1.1/kubernetes-design.md`'s
  corrections section for the full rationale.
- Carried forward, explicitly out of scope for this increment (per task
  §39): the Docker Desktop DNS issue itself, `scripts/deploy_remote.py`'s
  plaintext credentials, the `PI-NODE-1`/duplicate-server-a-UUID fleet
  oddities, the `cli_agent.py` fake-timestamp issue, and Phase 8D evidence
  revalidation.
- Incidentally discovered during this session, not touched (out of scope,
  acceptance-harness-only): `kind load docker-image`/`kind load
  image-archive` fail against Docker Desktop's containerd-backed image
  store with a `content digest ... not found` error for multi-layer
  images — worked around via image flattening for this session's testing
  only; this is a `kind`/Docker Desktop interoperability issue, not a
  PortForge defect, and is not something PortForge's implementation needs
  to account for (PortForge never loads images into any cluster).
