# v1.1-A Implementation: Foundation, Doctor & Protocol Compatibility

Implements exactly the scope of `docs/v1.1/roadmap.md`'s v1.1-A increment,
grounded in `docs/v1.1/doctor-design.md` and
`docs/v1.1/version-compatibility.md`. No DB migration, no CLI/API/
dashboard behavior change beyond additive fields and new, standalone
commands.

## 1. Canonical version source

Before this increment, `"1.0.0"` was hardcoded independently in **five**
places beyond `agent/pyproject.toml` itself — more than the planning
audit's own scan found (which caught only two): `__init__.py::__version__`,
`central_sync.py::AGENT_VERSION`, an inline literal in `runtime/agent.py`'s
heartbeat call, and two more inline literals in `cli_agent.py` (`agent
enroll` and `agent test`). All five now derive from a single new function,
`agent/portforge_agent/version.py::get_portforge_version()`
(`importlib.metadata.version("portforge-agent")`), which is the only
place any code reads "what version am I" from.

Regression coverage: `tests/test_version.py` (7 tests) proves every
sync/runtime/CLI payload that reports `agent_version` derives it from this
one function, not a separate literal — including the package's own
`__version__` dunder.

## 2. Protocol version

`agent/portforge_agent/version.py::PROTOCOL_VERSION = 1` and
`backend/app/services/compatibility_service.py::PROTOCOL_VERSION = 1` are
two independently-declared but semantically-linked constants (the agent
and backend are separate deployables — see
`docs/v1.1/architecture-audit.md` §2 for why true cross-process sharing
isn't possible, the same reasoning already established for
`DEFAULT_RANGES`). Deliberately **not** the same number as
`portforge_version`/`Settings.version` — see
`docs/v1.1/version-compatibility.md` for why conflating them would
produce false-positive warnings on every unrelated release.

Sent additively on `enroll`/`heartbeat` (`central_client.py`'s
`enroll()`/`heartbeat()` gained an optional `protocol_version` parameter,
included in the request body only when not `None`) and exposed
unauthenticated on `GET /api/health` (`HealthOut.protocol_version`, always
present).

## 3. Compatibility evaluation

`backend/app/services/compatibility_service.py::evaluate_protocol_compatibility()`
(server-side, evaluates an agent's reported version against Central's own)
and `agent/portforge_agent/version.py::evaluate_central_protocol_compatibility()`
(client-side mirror, used by `doctor`) both return one of three states:
`"compatible"` | `"warning"` | `"unknown"`. **Read-only, advisory,
non-blocking** — verified directly: `test_heartbeat_with_mismatched_protocol_version_warns_but_still_succeeds`
and `test_enroll_with_mismatched_protocol_version_reports_warning_not_rejection`
both assert HTTP 200 despite a deliberate mismatch, and no code path
anywhere raises or rejects based on this value.

`protocol_version` is **not persisted anywhere** — no new Host column, no
migration. `test_protocol_version_not_persisted_on_host` asserts this
directly against the real Host model.

## 4. `portforge doctor`

`agent/portforge_agent/doctor.py` — a pure, read-only aggregator over 11
checks, each reusing an existing capability (never a second
implementation): `cli_version`, `protocol_version`, `central_connectivity`,
`central_health`, `protocol_compatibility`, `agent_identity`,
`agent_service` (reuses `service_ops.status()`), `docker` (reuses
`collectors.docker.is_docker_available()`), `collector` (reuses
`discover_all_ports()`), `manifest` (reuses
`manifest.load_and_validate_manifest()`), `filesystem` (`os.access`
permission probes only — no file created/written/deleted).

### JSON contract

```json
{
  "contract_version": 1,
  "status": "ok" | "degraded" | "error",
  "portforge_version": "1.0.0",
  "protocol_version": 1,
  "checks": [
    {"id": "cli_version", "status": "ok", "message": "...", "details": {}},
    ...
  ]
}
```

Per-check `status`: `ok` | `warn` | `error` | `skip`. `overall` is the
worst severity across all checks (`error` > `warn`/`degraded` > `ok`/`skip`).
A legitimate optional absence (no manifest in cwd, Central sync never
configured, Docker not installed) is `skip` or `warn`, never `error` —
verified directly (`test_no_central_url_configured_is_skip_not_error`,
`test_no_manifest_is_skip_and_does_not_make_overall_unhealthy`,
`test_docker_unavailable_is_warn_not_error`).

### Exit codes

`0` — overall `ok` or `degraded` (no blocking diagnostic failure). `1` —
overall `error` (at least one check hard-failed). `2` is reserved for a
genuine CLI usage error (bad flags) — argparse itself raises this before
`_cmd_doctor` ever runs; doctor's own check logic never propagates an
exception that would produce it, by design (every check catches its own
underlying exceptions and reports `error`/`warn` instead).

### Human output

Plain-ASCII `PASS`/`WARN`/`FAIL`/`SKIP` markers (matching `cli.py`'s
existing convention for `next`'s validation-step rendering, for the same
Windows-console-code-page reason) — verified
(`test_doctor_human_output_has_plain_ascii_markers`).

## 5. Read-only proof

Two independent lines of evidence: `test_doctor_creates_no_files_in_project_root`
(a project directory's contents are byte-identical before/after a doctor
run) and `test_doctor_never_calls_any_mutating_client_method` (asserts
`create_allocation`/`release_allocation`/`sync_reservation`/`enroll` are
never called on the mocked `CentralClient`). Physical evidence (real
reservation/allocation counts before/after) is in §20 below.

## 6. Security review of doctor output

`test_report_never_contains_agent_token` and
`test_report_never_contains_admin_bootstrap_token_or_db_password` assert
directly against the serialized report. No check ever includes a token,
password, or connection string in its `message`/`details` — every check
that touches credentials (`agent_identity`) only ever reports presence/
absence, never the value.

## 8. Physical acceptance

Full evidence in the final report. Summary: Central runs as a Docker
container (`portforge-api`) as of the v1.0.0 release's containerization
work. Rebuilding that image to pick up this increment's backend changes
hit a real, pre-existing Docker Desktop DNS problem on this machine
(containers cannot resolve any external hostname right now, verified with
a plain `python:3.12-slim` container hitting `pypi.org` — not specific to
this build) — worked around by running Central as a bare `uvicorn`
process against the same real Postgres (port 55432), the exact method
every physical validation in this repository used before containerization.
All scenarios A-I from the increment's own physical-acceptance list were
run against this real, running Central: healthy doctor (human + `--json`,
parsed independently by a separate script), no-manifest, valid manifest,
invalid manifest (real typo caught), Central unavailable (bounded ~10s,
not a hang, all 9 non-Central-dependent checks still ran), Central
restored, Docker-unavailable (safe `PATH`-only simulation, real Docker
installation never touched, verified still healthy afterward), and a
real end-to-end allocation created and released with reservation counts
confirmed at 0 before and after every scenario. The `portforge-api`
Docker container itself is currently stopped, pending a rebuild once
Docker Desktop's DNS issue clears — the bare-process Central remains
running in its place so Central stays available.

## 9. Known limitations

- `filesystem` check uses `os.access()`, a best-effort permission probe —
  it does not account for unusual ACL configurations on some filesystems
  (documented in `doctor-design.md`'s own spirit of not overclaiming).
- `agent_service` check's message text is whatever `service_ops.status()`
  already returns (per-OS phrasing) — not normalized into a single
  cross-platform sentence; acceptable for v1.1-A's scope (aggregation, not
  a service-status redesign).
- Incidentally discovered, out of scope for this increment (not touched,
  per the "no unrelated cleanup/refactors" instruction): `cli_agent.py`'s
  `agent test` command sends a hardcoded fake timestamp
  (`"2026-01-01T00:00:00Z"`) to the real heartbeat endpoint, which could
  set a host's `last_seen` to a date in the past relative to "now" and
  make it appear STALE/OFFLINE immediately afterward. Flagged here for a
  future, separately-scoped fix — not addressed in v1.1-A.
