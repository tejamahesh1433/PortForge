# v1.5.0 RC Qualification Scope (Phases 15–18.6)

This file records the development and qualification phases that make up the
v1.5.0 release. Phase 19 (`docs/qualification/v1.5.0-rc.md`) is the
release-candidate gate that verifies the combined output of these phases.

## Phase 15 — Native Agent MCP

Branch: `feature/native-agent-mcp`

Implemented `portforge mcp serve` — a stdio MCP server exposing PortForge
capabilities to coding agents. Initial tool set: `portforge_capabilities`,
`portforge_workspace_discover`, `portforge_project_plan`. MCP protocol string
`2024-11-05`. No provider-specific implementation; same binary serves all
clients.

Provider validation evidence: Codex invoked tools live (`portforge_workspace_discover`,
`portforge_project_plan`). Claude Code connected but EXTERNAL BLOCKED (OAuth
expired — no PortForge defect). Antigravity: EXTERNAL BLOCKED (client not
installed).

## Phase 16 — Workspace Discovery

Branch: `feature/workspace-discovery`

`portforge workspace discover [path]` reads project manifests to enumerate
services and their internal ports without Central connectivity. Surfaces service
names, internal port numbers, and configuration paths to coding agents as a
read-only pre-planning step.

Physical evidence: Codex invoked `portforge_workspace_discover` live;
result contained correct service/port map from fixture workspace.

## Phase 17 — Environment, Target, and Ingress Model

Branch: `feature/environment-targets`

Extended the project manifest and MCP contract with named environments
(e.g. `development`, `production`) and named targets (e.g. specific host
identifiers) within each environment. Each target carries an ingress
configuration describing external-access semantics. `portforge_project_plan`
and `portforge_deployment_plan` became environment/target-scoped.

Provider validation: Codex invoked `portforge_project_plan` for
`development/windows` and `production/lenovo-prod` targets; both returned
structured `HOST_NOT_FOUND` (expected — dummy Central). Correct structured
errors, no invented ports.

## Phase 18 — Compose Deployment Orchestration

Branch: `feature/deployment-orchestration`

Full Compose deployment lifecycle on Central and agent:

- `host_deployments` and `deployment_revisions` schema (migration `d5e6f7a8b9c0`)
- Deployment state machine: APPROVED → CLAIMED → STARTING → SUCCEEDED / FAILED / ROLLED_BACK
- Claim lease (300 s, `secrets.token_urlsafe(32)`); token renewal; `409 DEPLOYMENT_CLAIM_MISMATCH` for stale tokens
- HTTPS package transfer with dual SHA-256 verification
- Compose validate + apply via agent adapter; archive path traversal protection
- Revision records on Central; rollback with `rollback_revision_id`
- `portforge_deployment_apply`, `portforge_deployment_status`, `portforge_deployment_rollback` MCP tools

Physical qualification (Phase 18.5): 33 PASS on Linux agent + Docker Desktop.
Defects found and fixed: SUCCEEDED without `revision_id`; absolute archive
paths accepted.

### Phase 18.6 — Deployment Safety + Interruption/Recovery

- Pre-apply host port recheck algorithm (FREE / EXPECTED_EXISTING_DEPLOYMENT / UNEXPECTED_OCCUPANT / UNKNOWN)
- `DEPLOYMENT_PORT_CONFLICT` and `DEPLOYMENT_PORT_STATE_UNKNOWN` error codes
- Interrupted / expired in-progress job re-delivery on heartbeat
- Residual TOCTOU documented: recheck narrows but does not eliminate the race between final check and Docker bind

Physical qualification (Phase 18.6): 48 PASS.
