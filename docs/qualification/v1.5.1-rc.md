## Mac root cause

### Reproduced

**YES** (structural + disposable physical LaunchAgent; production agent not modified during qualification).

### Old behavior (v1.5.0)

Generated plist:

```text
KeepAlive = { SuccessfulExit = false }
```

Meaning:

- Crash (non-zero exit) → launchd restarts.
- Clean exit (status 0), including upgrade restart shutdown and many sleep/wake paths → **job stays stopped**.
- No `NetworkState` directive → network return after sleep does **not** relaunch the agent.
- Central then shows STALE → OFFLINE until manual bootstrap/kickstart.

### New behavior (v1.5.1)

```text
KeepAlive = { SuccessfulExit = false, NetworkState = true }
```

Plus kickstart hardening:

- `kickstart` timeout raised to 60s.
- On kickstart timeout, re-check `launchctl print` state; succeed if already running.
- If kickstart fails and plist exists, one `bootstrap` then retry `kickstart`.
- `status` treats `state = running` as success; loaded-but-not-running as failure.

`SuccessfulExit=false` is retained so `portforge agent service stop` does not fight launchd.

## Linux investigation (DEFERRED)

### Reproduced

**YES** (code-path analysis + production canary history). Disposable live `systemctl --user` self-upgrade was **not** re-run against production hosts (production freeze).

### Root cause

1. `upgrade/platform_restart.py` `restart_via_systemd()` runs `systemctl --user restart <unit>` **synchronously from inside the unit**.
2. systemd stops the cgroup with `KillSignal=SIGTERM`.
3. Python surfaces child killed-by-signal as `returncode == -15`.
4. Upgrade handler reports **FAILED** after already posting **RESTARTING**.
5. systemd still starts the new MainPID → host HEALTHY on new version with a false FAILED upgrade row.

### Why not included

- Blind “treat -15 as success” is unsafe.
- Correct fix is `--no-block` (or detached helper) **plus** the missing SUCCEEDED completion path (shared with Windows).
- Physical disposable systemd-user qualification required if INCLUDE — not available without mutating production agents.

## Windows investigation (DEFERRED)

### Reproduced

**YES** (code + production observation: agent 1.5.0 HEALTHY, upgrade row RESTARTING).

### Root cause

1. Agent `run_upgrade` reports through **RESTARTING** only; never posts `VERIFYING_HEALTH` / `SUCCEEDED`.
2. Comments claim Central infers SUCCEEDED from heartbeat version match — **not implemented** in `agents.py` heartbeat.
3. `get_pending_for_host` only returns APPROVED/WAITING_FOR_AGENT, so the new process never sees the in-flight upgrade again.

### Why not included

- Fix belongs in Central heartbeat reconciliation (strict: same host, non-terminal ∈ {RESTARTING, VERIFYING_HEALTH}, `agent_version == target_version`, never rewrite FAILED).
- That is a Central functional change → API 1.5.1 image + disposable Windows physical gate.
- Out of minimal Mac-lifecycle patch scope for this RC.

Historical production FAILED/RESTARTING rows were **not** rewritten during this qualification.
