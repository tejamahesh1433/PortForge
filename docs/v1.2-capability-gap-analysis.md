# PortForge v1.2 Capability and Architecture Gap Analysis

## 1. Current Architecture Map

### Agent Architecture
The `portforge_agent` runs on individual developer machines. It handles port discovery (via psutil/netstat and Docker APIs) and real-time bind probing to evaluate port availability. It communicates with the Central backend via REST API using HTTP POST (heartbeats, observations, probes) and can be run interactively via the `portforge` CLI or as a background service via Task Scheduler (Windows), launchd (macOS), or systemd (Linux).

### Central/Backend Architecture
The backend is a FastAPI application interacting with an SQLite database via SQLAlchemy. It acts as the central control plane, receiving port observations and heartbeats from agents, maintaining the master inventory of host ports, project reservations, and API allocations. It provides endpoints for agent synchronization, project allocation, and dashboard UI rendering.

### Dashboard Architecture
A lightweight frontend providing visibility into fleet overview, host details, live port inventory, projects, and active allocations/reservations. The dashboard calls the backend APIs but currently has no authentication (trusted LAN assumption).

### Database Models
- `Host`, `HostProbe`
- `CurrentPortObservation`, `PortObservationEvent`
- `CentralReservation`, `Allocation`
- `Scan`, `ActivityEvent`, `AgentCredential`, `EnrollmentToken`

### Capabilities
The system currently performs port discovery and detection (native + Docker). It supports project reservations via local `.portforge.yml` manifests (`portforge sync-reservations`), interactive recommendations (`portforge next`), real bind probes (`portforge check`), and atomic API allocations (`portforge allocate api`). It also provides tools to mutate environment files and compose definitions (`portforge config`).

## 5. Project Config Mutation

Current Support:
- **.env / .env.example**: COMPLETE (dotenv_editor.py). Modifiable, staled-file protected, easily backed up.
- **Docker Compose**: COMPLETE (compose_editor.py). YAML modification preserves comments.
- **Next.js / FastAPI / Node / Vite**: PARTIAL. Primarily environment variables.
- **Kubernetes hostPort/nodePort**: COMPLETE (k8s_editor.py).
- **Rule Preservation**: Kubernetes `containerPort`, `Service` port, and `targetPort` are strictly preserved/ignored during conflict resolution to maintain internal networking. Rollbacks are supported via `config_manager.py`.

## 6. portforge.yml Manifest

The manifest supports defining project identity, services, preferred ports, ranges, and protocol. Allocation policies and host selections are partially supported. Backwards compatibility requires treating v1 manifests gracefully, preserving `project` and `services` schemas.

## 7. Concurrency / Race Safety

- **Two developers/agents allocate simultaneously**: Safe. SQLite/SQLAlchemy transactions in `create_allocation` use standard locking.
- **Two hosts request same port**: Safe. Handled by backend constraints.
- **Probe says free but process binds before allocation**: TOCTOU risk. The backend allocates based on the last probe/observation. Real binds can still fail locally.
- **Central/Agent unavailable**: Local fallback exists for discovery (`check`, `next`), but `allocate api` strictly requires Central.

## 9. Dashboard Gap Analysis
Existing pages include fleet overview, active reservations, conflicts, and basic host details.
**v1.2 UI Capabilities**: Adding actionable buttons for "Release Allocation" or "Re-probe Host" would add significant value without full redesign.

## 10. Security Boundaries
Trusted LAN assumption holds. External AI coding-agent API interactions should remain restricted to local agent commands or unauthenticated LAN APIs (which do not expose secrets). `allocate` and `config` mutate state and must support dry runs.

## 11. Backwards Compatibility
Protocol = 1, Contract = 1 can be strictly maintained. No protocol bump is technically required as API additions can be backwards compatible. Database migrations will be minor.

## 12. Test Coverage Map

## 14. Proposed v1.2 Phases

- **Phase 1 — foundations**: Add range boundaries to allocation backend. No contract bump. **(COMPLETED)**
- **Phase 2 — allocation engine**: Extend CLI to request specific ranges and verify allocations. **(COMPLETED)**

## 15. Non-Goals
- Browser authentication
- Cloud SaaS control plane
- Arbitrary remote command execution
- Automatic router/firewall configuration
- Kubernetes `containerPort`, `Service` port, `targetPort` rewriting
- Provider-specific coding-agent coupling
- Paid infrastructure dependencies

## Phase 3 status

Phase 3 project workflow is implemented and validated around the existing canonical portforge.yml/portforge.yaml manifest. Legacy .portforge.yml semantics remain unchanged; project init, local validation, and observational status use safe parsing, bounded project discovery, existing allocation data, and explicit partial Central availability. No protocol, contract, database, or production behavior changes are included.

## Phase 4 status

Phase 4 safe project configuration mutation is complete. Existing dotenv, Docker Compose, and Kubernetes host-level mutation paths remain one shared engine with explicit targets, containment checks, stale-file rejection, atomic writes, post-write validation, rollback, and secret-safe output.

## Phase 5 status

Phase 5 provider-neutral automation is complete. Existing JSON commands, stable IDs, lifecycle error codes, bounded verification, plan/apply safety, retry behavior, and secret redaction are documented and subprocess-tested without provider-specific integration.

## Phase 6 status

Phase 6 dashboard work is complete and frozen. The existing operator screens now include typed allocation create and verify actions, contextual release semantics, mixed-version and offline-host handling, and explicit separation between Central lifecycle state and local project configuration. No protocol, agent contract, database schema, production fleet, or public deployment boundary changes were made.
