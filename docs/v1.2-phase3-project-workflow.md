# PortForge v1.2 Phase 3: Project Workflow

Phase 3 consolidates project discovery, manifest validation, and observational
status around the existing manifest and allocation models.

## Manifest types and precedence

The canonical project manifest is `portforge.yml`; `portforge.yaml` is an
equivalent fallback. When both canonical names exist, `portforge.yml` wins.
The legacy `.portforge.yml` remains a separate configuration format used by
legacy reservation and synchronization workflows. It is never renamed,
converted, or silently reinterpreted.

## Discovery and initialization

Project commands accept an explicit manifest path. Without one, commands look
in the current directory and then its bounded parent directories, stopping at
the filesystem root. An explicit path always wins.

`portforge project init` derives a safe project name from the current directory
when one is not supplied and creates a minimal manifest. It does not allocate
ports, probe agents, start services, or edit application configuration. Service
entries are left empty when detection is not confident. Existing manifests are
never overwritten implicitly. The write is atomic.

## Validation

`portforge project validate` parses YAML with `yaml.safe_load` and validates the
existing manifest schema locally. It checks project identity, protocols, ports,
requested ranges, preferred-port inclusion, and supported target fields. Range
syntax is the existing Phase 1 `MIN-MAX` contract with bounds 1 through 65535.
Validation does not allocate, release, verify, probe, rewrite, or contact
Central in its normal local mode. The established explicit `--url` mode retains
its prior host-reference resolution behavior for compatibility.

## Status

`portforge project status` is observational. It combines manifest services with
the existing Central allocation list when Central is available. Matching uses
the stable project name and service name; it does not infer identity from a
directory basename or port number. A valid manifest without an allocation is
reported as `UNALLOCATED`. If Central cannot be reached, the manifest remains
available and the result reports `central_available: false` with a structured
error. Status never allocates or performs verification.

JSON mode (`--json`) is available for init, validate, and status. JSON output
contains data only on stdout and represents partial Central availability
explicitly.

## Allocation bridge and precedence

The existing allocation engine is reused. Manifest requests can supply protocol,
preferred port, and requested range through the existing allocation body; no
second allocator was introduced. Existing allocation behavior remains the
source of truth. Where a value is available from multiple sources, explicit CLI
arguments take precedence over manifest constraints, which take precedence over
allocator defaults. Host assignment remains an allocation-time concern unless a
manifest already contains a supported target.

## Services and limitations

Multiple named services are supported independently, including mixed allocated
and unallocated projects. The existing backend bundle model can represent
multi-port allocations, but the manifest request model does not invent a new
per-service multi-port syntax; projects needing that capability use the
existing allocation APIs. Host policy is preserved where already supported and
is otherwise not persisted as a physical hostname or IP in portable manifests.

## Compatibility and non-goals

Protocol version remains 1 and the agent contract remains 1. No database
migration is required. Legacy `.portforge.yml`, existing allocations,
reservations, and lifecycle behavior remain compatible. Phase 3 does not
orchestrate runtime processes, mutate application configuration, redesign the
dashboard, or add provider-specific integrations.
